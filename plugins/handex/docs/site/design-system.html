Design System do Handex

O que é esta página: referência viva do design system da interface do próprio plugin Handex — não o DSC (Design System CAIXA), que é o sistema externo auditado pelo plugin. Cada componente abaixo é renderizado com o CSS real do Handex (cores, fontes, radius, espaçamentos idênticos ao código-fonte), não apenas descrito em texto.

Como usar: antes de criar uma tela, botão ou card novo, confira aqui o padrão já existente. Toda cor/tamanho/componente citado tem uma referência de arquivo:linha entre parênteses — se o código atual divergir do que está aqui, é dívida técnica (seção 7), não uma segunda opção válida.

Escopo desta versão: cobre os padrões estruturais reutilizados entre as 6 ferramentas do plugin (Guia, Dados do Projeto, Escanear Tokens/Handoff, Anotar Specs, Anotar Medidas, Fluxos de Tela) — não cobre elementos gerados no canvas do Figma (specCard, conectores), que seguem a Plugin API e estão documentados inline em code.js.

Arquivo local autocontido, versionado no repositório — não é publicado como site (sem GitHub/GitLab Pages, sem hospedagem externa). Funciona abrindo direto no navegador (file://), sem instalar nada e sem CDN externo obrigatório.

2. Tipografia

Fonte única: Inter, sans-serif (plugin.css:3), forçada com !important em headings/labels/pills (plugin.css:497-501). Escala confirmada via varredura de text-[Npx] em todo o código (contagem real de ocorrências entre parênteses).

Título de destaque — 22px extrabold (4 ocorrências)

Título de modal grande / header de view — 18px bold (15 ocorrências)

Título de modal médio — 15–16px extrabold (4 ocorrências)

Título de modal pequeno — 14px bold (10 ocorrências)

Corpo de botão / título de card — 13px (29 ocorrências)

Texto de card padrão / body — 12px (163 ocorrências — o tamanho mais usado no plugin)

Subtítulo de header / label de modal — 11px (196 ocorrências)

Hints, descrição de card, badge — 10px (223 ocorrências)

Contador de caractere, uppercase pill — 9px (166 ocorrências)

Menor tamanho em uso — 8px (36 ocorrências)

Pesos: font-bold é o padrão de botão/label; font-extrabold reservado a títulos de destaque e CTAs primários; font-semibold/font-medium para ênfase secundária.

Os tokens nomeados text-3xs/text-2xs/text-xs-plus/text-md ainda não existem em fontSize do tailwind.config.cjs — o código inteiro usa valores px arbitrários (text-[10px] etc.) em vez de nome de classe. Os valores acima são os corretos, só não têm nome de token ainda.

Catálogo completo — 97 de 97 ícones confirmados em uso real no código, 100% cobertos. Ícone decorativo segue o tamanho do contexto (w-3.5–w-5); ícone interativo isolado segue a regra de 40×40px de área de toque da seção de Botões. Pares que alternam no mesmo botão (eye/eye-off, lock/lock-open, sun/moon) aparecem como cards distintos, um por estado.

Peso visual e tamanho de ícones-irmãos

Peso visual uniforme (plugin.css): todo ícone Lucide nasce com stroke-width: 2 (padrão da lib, calibrado para o viewBox nativo de 24px). Como o plugin usa ~7 tamanhos diferentes de ícone (w-2.5 a w-6) no mesmo viewBox, o mesmo traço de 2px parece mais grosso nos ícones pequenos e mais fino nos grandes — regra CSS global compensa por faixa de tamanho:

Classestroke-width
w-2.5, w-32.5
w-3.5, w-42.25
w-4.5 e acima2 (padrão nativo, sem compensação)

Ícone novo herda essa regra automaticamente por classe de tamanho — não é preciso declarar stroke-width manualmente em nenhuma tag <i data-lucide>.

Ícones-irmãos (mesma linha/grupo, mesma hierarquia de ação) usam sempre o mesmo tamanho. A compensação de stroke-width acima resolve peso percebido entre categorias de tamanho distantes — não resolve, e não deveria precisar resolver, dois ícones lado a lado com tamanhos ligeiramente diferentes sem motivo (ex: w-5 ao lado de w-4.5, ou w-3.5 ao lado de w-3 na mesma linha de ações). Isso é bug de inconsistência, não peso visual — a correção certa é igualar o tamanho, não ajustar stroke. Regra prática: antes de declarar o tamanho de um ícone novo, olhar o que os ícones vizinhos no mesmo componente já usam e copiar.

Exceção deliberada: o botão "voltar" do header (arrow-left, sempre w-5) é maior que os botões de ajuda/onboarding ao lado (graduation-cap/circle-help, sempre w-4.5) — hierarquia intencional (ação de navegação primária > ação secundária de suporte), não inconsistência.

5. Componentes

Botões — catálogo de 6 variantes

Fonte: varredura de classes literais em views/*.html. Todo botão do Handex é uma destas 6 variantes.

Nota: .hx-btn-primary/.hx-btn-outline/etc. são nomenclatura desta documentação, não classes CSS reais do plugin — não existem em plugin.css nem em nenhum arquivo do código. No código real, escreva o Tailwind puro citado em cada legenda abaixo (ex: bg-blue-500 hover:bg-blue-600 text-white rounded-2xl font-bold) diretamente no botão.

Primária: bg-blue-500 hover:bg-blue-600 text-white rounded-2xl font-bold. Destrutiva: bg-red-500 hover:bg-red-600. Branco/outline neutro: bg-white border border-gray-200 rounded-2xl py-3 text-[12px] font-bold (dimensão única desde 2026-08-26). Sub-variante link externo: mesma dimensão, borda/texto blue-500. Disabled (todas as 6 variantes, incluindo botão-ícone com/sem fundo): disabled:opacity-40 disabled:cursor-not-allowed, cor de fundo original preservada por baixo da opacidade — hover desativado junto.
Secundária/ghost sobre header azul: fundo bg-white/10, hover:bg-white/20. Botão-ícone interativo isolado: container w-10 h-10 (40×40px de área de toque real).
Ícone utilitário com fundo: bg-white border border-gray-200 rounded-2xl, cor de hover semântica (vermelho para descarte). Disabled (segundo botão): mesma regra das variantes de texto — disabled:opacity-40 disabled:cursor-not-allowed. Usar sempre que a ação não tiver o que fazer (ex: "Baixar" e "Limpar" na home, sem nenhum dado documentado ainda).

Resolvido em v6.11.0 (2026-09-10): auditoria ampla encontrou e corrigiu ~20 botões de ação primária com hex solto (incluindo as 4 ocorrências de hex pré-reversão de marca antes listadas aqui) e todos os botões "Cancelar/Voltar/Fechar" em cinza sólido ou texto puro sem padrão — normalizados para as classes Tailwind reais das variantes primária/outline. Achado principal: o botão de ação do onboarding (onboarding.js) usava uma cor por ferramenta (parte do sistema de identidade visual do modal), o que também colorá o botão de avançar com tons sem significado semântico (indigo, purple) — corrigido para sempre usar a variante primária (azul de marca); a cor por ferramenta permanece só nos elementos decorativos (ícone, barra de progresso, destaque de propósito).

6.5 Acessibilidade

Regras de base (independentes de tema/cor) exigidas em todo componente interativo do plugin:

  • Área de toque mínima de elemento interativo: 40×40px (botões-ícone, ver seção 5, Botões).
  • Accordion: sempre aria-expanded no elemento que controla a expansão.
  • Foco: todo modal precisa de focus trap (padrão já implementado globalmente em core.js:2365-2408 — reaproveitar, não reimplementar por modal).
  • aria-label obrigatório em todo botão-ícone sem texto visível.

Contraste de cor (WCAG 2.1 AA) — auditoria 2026-08-26

Piso adotado para toda a UI do plugin (não confundir com o DSC, que tem sua própria auditoria de acessibilidade sobre o produto CAIXA — este piso é sobre a própria interface do Handex):

  • Texto normal (<18px, ou <14px bold): mínimo 4.5:1.
  • Texto grande (≥18px, ou ≥14px bold) e ícones/componentes gráficos não-decorativos (glifo de botão-ícone, borda de card informativo): mínimo 3:1.
  • Cálculo pela fórmula de luminância relativa padrão WCAG 2.1 (não por inspeção visual). Cores com opacidade (text-white/70, text-[#005ca9]/60, dark:bg-blue-900/10 etc.) são compostas (alpha-blend) sobre o fundo real antes do cálculo — a opacidade nominal da classe não é o contraste real.

Regras específicas descobertas nesta auditoria (motivadas pela reversão de marca de 2026-08-26, #3d3dff→#005ca9, que reduziu a luminância da cor de ação primária):

  1. Opacidade mínima de texto/ícone branco sobre o header azul (bg-blue-500/#005ca9): text-white/70 cai para ~4.15:1 — só passa porque hoje é usado exclusivamente em ícones puros (piso 3:1), nunca em rótulo de texto corrido. Não usar text-white com opacidade abaixo de /70 sobre bg-blue-500 em nenhum contexto novo; se o elemento for texto legível (não só glifo decorativo), usar opacidade cheia (text-white, sem /opacity) ou text-blue-100.
  2. Banner de onboarding (bg-blue-500/5 light): o botão de dispensar (ícone x) precisa de pelo menos text-[#005ca9]/80 sobre esse fundo claro — /60 reprova o piso de ícone (3:1). Título/corpo do banner (text-[#004d8d]//80) já passam, mas com pouca folga.
  3. Nenhum texto/borda azul (text-[#005ca9]) pode ficar sem par dark: explícito. Um elemento que herda a cor light (#005ca9) sobre um fundo escuro (dark:bg-dark-bg, #0f172a) cai para ~2.64:1, reprovando os dois pisos. Todo uso de text-[#005ca9]/border-[#005ca9] em bloco que também tem uma variante dark:bg-* precisa do par dark:text-blue-400 (ou mais claro)/dark:border-blue-400.
  4. Texto secundário (text-slate-400/text-slate-500) só é seguro sobre card branco (bg-white/bg-light-surface), não sobre o fundo geral da view (bg-light-bg, #eef2f7). Qualquer texto slate-400/slate-500 que fique diretamente sobre o fundo da view (sem um card branco por baixo) precisa subir para text-slate-600 no light mode.
  5. Badge de categoria (fill claro + texto colorido) precisa reavaliar o par a cada vez que o fill for reaproveitado de outro contexto. As cores de categoria de spec foram herdadas do canvas do Figma (onde o piso de contraste não se aplica da mesma forma) e reprovaram quando usadas como texto de UI sobre os mesmos fills claros. Um tom que funciona bem como stroke de card no canvas não necessariamente funciona como texto de badge na UI.

7. Dívida técnica observada (código vs. padrão declarado)

Lista completa de prioridade, espelhada de docs/design-system-handex.md §9 (fonte normativa) — cada item é uma correção pontual, não um redesenho:

  1. Paleta de categoria de spec — unificar Ficha exportada (handoff.js:736-741), card do canvas (_CAT_COLORS, specifications.js:463-468) e legenda do modal de ajuda (modals.html:396-418), hoje 3 conjuntos de hex diferentes para as mesmas 4 categorias.
  2. Bug adormecido de verde/laranja — plugin.css:127-134 faz button.bg-green-600/.bg-green-500 herdar #935300 (cor de hover do laranja de alerta). Corrigir antes que um botão verde real seja criado.
  3. Escala tipográfica sem token nomeado — adicionar 3xs/2xs/xs-plus/md ao fontSize do tailwind.config.cjs; todo o código usa px arbitrário hoje.
  4. rounded-xl residual — migrar para rounded-2xl nos botões-ícone de utilidade e na versão "editar" do flow-type-card-modal. 141 ocorrências reais em views/*.html, incluindo o botão "voltar" do header padrão de toda view — o padrão declarado (rounded-2xl universal) e o uso real convivem sem terem convergido.
  5. Radius de card via seletor de id — mover [id$="-card"] { border-radius: 16px !important } (plugin.css:451-465) para classe Tailwind direta no HTML.
  6. z-index de modal sem constante nomeada — extrair Z_MODAL_BASE/Z_MODAL_STACKED/Z_MODAL_LIGHT (ou equivalente) em vez dos valores mágicos (z-[1000]/z-[1200]/z-[200]) hoje espalhados no HTML.
  7. 4 dialetos de accordion → 1 — migrar guide.html (onclick inline sem aria-expanded), o Briefing Estratégico (div role="button") e os chevrons próprios (.journey-chevron, .group-chevron) para toggleAccordion(btn, nodeId) (core.js:2696), o padrão oficial.
  8. Empty state do hub de Frames — hoje é HTML estático (handoff.html:66-72) em vez de usar a função JS compartilhada das outras 3 ferramentas.
  9. Nomenclatura "Escanear Tokens/Frames/Handoff" — card na home diz "Escanear Tokens", id interno é view-frames, arquivo é handoff.html; nome canônico proposto é "Handoff" (reflete o papel real da tela como hub central do frame — scan + medidas + specs + conformidade), ainda não convergido nas 3 pontas.
  10. Hex de brand direto no HTML — migrar bg-[#005ca9]/hover:bg-[#004d8d] para as classes nomeadas bg-blue-500/hover:bg-blue-600. Maior volume de mudança da lista — não precisa ser feito de uma vez, mas todo código novo já nasce usando a classe nomeada.
  11. #1E293B hardcoded — substituir por text-slate-800 dark:text-white onde aparece como cor de título (é literalmente o mesmo hex).
  12. Resolvido em 2026-08-26 — os 2 hovers isolados (home.html:163, modals.html:1245) que usavam #004d8f/#005a8e (azul institucional pré-reversão de marca) já convergiram para blue-600 (#004d8d) como parte da reversão de marca — não é mais dívida.
  13. Código morto de wizard sequencial — core.js:2092-2181 e modals.html:984-1014 (check-designs-modal) sem tela viva que os alimente. Não é dívida de design, mas deveria ser removido antes de qualquer nova geração de UI se acumular em cima.
  14. Onboarding duplicado — guide.html e onboarding.js (ONBOARDING_TOOLS) mantêm conteúdo quase idêntico por disciplina manual; já divergiram uma vez. Não é dívida de design system em si, mas afeta a camada de conteúdo que acompanha os componentes.
  15. Resolvido em 2026-08-26 — disabled:bg-gray-300 (modals.html:1115, botão "Salvar Cenário") migrado para disabled:opacity-40. Confirmado durante a auditoria de contraste que o padrão antigo reprovava gravemente (branco sobre cinza-300 = 1.49:1) — não é mais dívida.
  16. Badge "Comportamento" da legenda de tipos de spec passa no piso, mas com pouca folga — modals.html:403 (text-[#93537D] sobre bg-[#F8EAF3]) mede 4.53:1, acima do piso de 4.5:1 mas por pouco. Qualquer ajuste futuro de fill/tom deste badge específico deve reverificar o contraste antes de publicar.
  17. Assimetria de contraste do botão "dispensar" do banner de onboarding entre temas — no light mode o ícone precisou subir de /60 para /80 de opacidade para passar do piso de 3:1. O par dark (dark:text-blue-300/60) já passava a 3.93:1 e não foi tocado — os dois temas usam frações de opacidade diferentes hoje para o mesmo elemento visual. Um ajuste futuro que tente "unificar" a opacidade entre temas precisa recalcular, não presumir que o mesmo valor serve para os dois.
  18. Paleta de categoria de scan (11 cores, tailwind.config.cjs:69-93 safelist) parece órfã — nenhum arquivo em modules/*.js ou views/*.html constrói dinamicamente as classes bg-{cor}-50 text-{cor}-600 border-{cor}-200 descritas no comentário do safelist. A função _getCatColor que existe hoje (specifications.js:458) é sobre categoria de spec (info/comportamento/regra/api), não sobre esse ciclo de 11 cores. Se a feature que consumia essa paleta foi removida, o safelist deveria ser removido junto (reduz o CSS compilado); se ainda existe em algum lugar não encontrado, precisa de investigação antes de confiar nos tons — 4 das 11 cores (lime-700, rose-600, pink-600, teal-600, sobre seu par -50) reprovariam o piso de 4.5:1 se algum dia voltarem a ser renderizadas.
  19. Contadores de caractere abaixo do piso de contraste — text-[9px] text-slate-400 dark:text-dark-muted (ex: dados-projeto.html:45,96,115,134,146, modals.html:127 e ~15 outras ocorrências) reprova o piso de 4.5:1 sobre card branco (~2.6:1). Não corrigido por ser anotação secundária de apoio (contagem "0/100" ao lado do label, nunca a única fonte da informação) — mudar a cor de ~20 pontos do produto de uma vez foge do "ajuste pontual" desta rodada, mas qualquer revisão de formulário/input deve tratar isso como pendência de contraste real, não estética.

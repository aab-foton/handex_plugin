1. Schema de dados (hacData)

O hac não tem conceito de "frame"/múltiplas telas (diferente do Handex). Existe um único array de verdade por tipo, sem duplicação avulso+por-frame — essa duplicação foi a causa raiz de um bug conhecido do Handex (specs "sumindo" por haver duas fontes de verdade divergentes); o hac nasce sem esse padrão por decisão deliberada.

hacData = {
  _schemaVersion: 1,
  a11yAreas: [],         // Áreas Marcadas — card clicável, abre workspace própria (seção 8b)
  a11ySpecs: [],         // Especificações de acessibilidade (5 categorias)
  tabOrderItems: [],     // Ordem de Tabulação (por área, arquitetura de cópia de frame)
  a11ySwipePaths: [],    // Trilha de Swipe (por área, N pontos — ver seção 8d)
  currentUser: null,     // Usuário Figma identificado automaticamente (sem login)
  projectOrigin: null,   // 'web' | 'mobile' | null — ver seção 3
  activeSectionName: null, // nome da Section de specs ativa — ver seção 8
}

Definido em src/plugin/modules/core.js, espelhado em variáveis globais soltas (a11yAreas, a11ySpecs, tabOrderItems) que são a fonte de verdade real durante a sessão — hacData é remontado a partir delas só na hora de persistir (saveToStorage()). a11ySwipePaths é a EXCEÇÃO — vive só dentro de hacData, sem variável global espelhada (todo ponto de leitura acessa hacData.a11ySwipePaths diretamente).

_schemaVersion continua fixo em 1 desde a origem do plugin — todas as mudanças de schema tratadas até aqui (variantes mobile, projectOrigin) foram tratadas como aditivas, migração por ausência de campo, não por número de versão.

a11yAreas[]

Nota de terminologia (2026-09-10): o termo de UI/produto mudou de "Área"/"Área Marcada" para "Tela"/"Tela Selecionada" (botão "Marcar Área" → "Selecionar Tela"), por decisão do usuário — mudança só de texto visível. Nomes internos de código, variáveis (a11yAreas, areaId, a11yAreaId), funções (openA11yAreaModal, _a11yAreaAccordionEl, etc.) e esta documentação técnica permanecem com o termo "área", sem migração — é implementação interna, não risco de quebra e decisão explícita de não tocar nisso agora.

Selo numerado de seção/tela marcado no canvas. Campos: id, number, label, targetNodeId. Não tem campo origin próprio — a origem web/mobile deixou de ser calculada por área (ver seção 3). Na UI, cada área é renderizada como card clicável na listagem principal (não mais accordion expansível in-line) — clicar abre a workspace própria da área, com 4 tabs. Ver seção 8b, "Workspace de Área", para o desenho completo.

a11ySpecs[]

Cada spec pertence a uma categoria (a11yType: elemento | estrutura | titulo | decorativo | informacoes) e a uma Área Marcada (a11yAreaId). Campos principais: id (nodeId real do specGroup no canvas), targetNodeId, letter, color/fillColor, properties[] ({key,label,value}), a11ySubtype (chave crua da subvariante, usada pelo backend pra ajustar a instância aninhada do componente real importado), a11yOrigin ('web' | 'mobile', gravado no momento da criação — nunca recalculado depois), a11ySourceLib, a11yDscComponentName (nome real do component set DSC, quando resolvido), needsReview (boolean — seção 4), locked (specs de a11y nascem sempre travadas), visible.

tabOrderItems[]

Populado pela arquitetura de cópia de frame (_createTabOrderCloneForArea em code.js) — nunca desenha sobre o design original. A cópia vive dentro de uma Section dedicada no canvas, separada da Section de specs — ver seção 8.

a11ySwipePaths[]

Trilha direcional de N pontos por área (substituiu swipeOrderItems[], depois a11ySwipeFlows[] — histórico completo na seção 8d). Schema: {id, points: [{nodeId, nodeName}, ...], areaId, createdAt}. Exclusivo de projetos mobile.

projectOrigin

Ver seção 3 — origem web/mobile do arquivo inteiro, não por área.

activeSectionName

Ver seção 8 — nome da Section de specs ATIVA no canvas nesta sessão do arquivo. null = ainda não escolhida explicitamente, resolve pro nome fixo original sem migração. Só ganha valor quando o designer opta por "Iniciar nova Section" no aviso de documentação já existente, ao Marcar Área.

Persistência

saveToStorage() remonta hacData a partir das variáveis globais e envia save-storage pro backend. Isolamento por arquivo real do Figma: chave hacData:${figma.fileKey}.

Arquivos ainda não salvos não têm figma.fileKey. Uma chave de fallback fixa (hacData:unsaved) existiu até 02/09/2026, mas causava vazamento real de dados entre projetos/clientes diferentes: como clientStorage é escopado por instalação do plugin (não por arquivo/aba), todo arquivo não-salvo lia e escrevia na MESMA chave. _getHacDataStorageKey() agora retorna null nesse cenário: o arquivo não-salvo sempre abre com hacData zerado e nada é gravado até o arquivo ganhar um fileKey real (primeiro save). Consequência aceita: fechar o plugin no meio do trabalho num arquivo nunca salvo perde o progresso da sessão — preferível a corromper silenciosamente dados de outro projeto.

clear-cache reseta a11yAreas/a11ySpecs/tabOrderItems/a11ySwipePaths e também projectOrigin/activeSectionName — decisão deliberada: "Limpar Cache" deve simular um arquivo novo por completo, incluindo perguntar a plataforma de novo e voltar a criar Áreas na Section fixa original, não numa versionada que o designer possa ter escolhido antes. currentUser é preservado (identidade/configuração de ambiente, não conteúdo do projeto).

Diferenças reais web vs. mobile por categoria

  • Nível de Título: web usa H1-H6 (hierarquia real); mobile usa um identificador único "H", sem distinção de nível, porque React Native não tem o conceito de hierarquia de heading do HTML. Desde 2026-09-09 o <select> de nível (#a11y-titulo-nivel-select) trava as opções pela origem da área — só H1-H6 ficam habilitadas em web, só "H (mobile)" fica habilitada em mobile (_applyA11yTituloOriginLock em accessibility.js, chamada de dentro de updateA11yTituloFields).
  • Estrutura da Página: sem componente mobile publicado — a lib "Design Acessível | Super App" não modela landmarks semânticos, então o marcador visual continua usando o wrapper desktop (comportamento aceito, não é bug). A partir de 2026-09-09, porém, a Nota de Código do subtipo "Marco de Navegação" diferencia por origem: em área web usa as tags HTML reais (<header>, <nav>, <main>, <aside>, <footer>); em área mobile usa accessibilityRole (React Native não tem essas tags) — mesmo princípio já aplicado em Nível de Título. Ver A11Y_CONTENT.estrutura.marcoMobile em accessibility.js.
  • Elementos e Imagens: mobile tem 3 sub-variantes (Componente, Link, Texto Alternativo) com campos próprios — seção 5. Web usa o catálogo de 16 componentes curados da lib "Design Acessível" desktop.
  • Elemento Decorativo: card real importado nas duas origens; conteúdo textual (Descrição/Notas de Código) é fixo/hardcoded na lib publicada em ambas — limitação real do componente Figma, não do plugin.
  • Informações Adicionais: formato livre, sem diferenciação documentada mobile/web.

3. Origem do projeto (web/mobile) — histórico de 3 decisões no mesmo dia

Fase 1 (anterior): voto de maioria por área. area.origin era calculado a partir da proporção de componentes web vs. mobile detectados dentro de cada Área Marcada, recalculado a cada "Reescanear". Frágil: dependia de haver componentes reais suficientes detectados, e podia mudar retroativamente entre scans da mesma área.

Fase 2 (revertida no mesmo dia): perguntar a cada ação. O voto de maioria foi removido e substituído por uma modal bloqueante ("Este handoff usa qual biblioteca?") perguntada toda vez que uma ação precisava saber a origem: Marcar Área, Detecção Automática, Ordem de Tabulação. Problema real: quando "Marcar Área" tem auto-detecção ligada, ela dispara a Detecção Automática em sequência imediata — o designer via a mesma pergunta aparecer duas vezes seguidas, indistinguível de um bug de loop.

Fase 3 (estado atual): configuração única por projeto. A origem é uma característica do arquivo inteiro, nunca mista (confirmado repetidamente pelo usuário: "se é um projeto mobile, tudo referencia mobile"). Implementação:

  • getA11yProjectOrigin() lê hacData.projectOrigin. isA11yMobileProject() (2026-09-09, ao lado dela) é o atalho para getA11yProjectOrigin() === 'mobile' — usado sempre que a pergunta é só "este projeto é mobile?", nunca substitui checagens de modal.dataset.a11yOrigin (origem de uma spec/elemento individual, conceito diferente e não relacionado à origem do arquivo inteiro).
  • ensureA11yProjectOriginThen(onReady) é o ponto único que toda ação que precisa da origem deve chamar: se já definida, chama onReady(origin) direto, sem abrir modal; se não, abre a modal bloqueante uma única vez, persiste a resposta, e só então chama onReady.
  • As 3 ações que precisavam disso (Marcar Área com auto-detecção, Detecção Automática, Ordem de Tabulação manual e automática) foram migradas para ensureA11yProjectOriginThen — nenhuma pergunta de novo depois da primeira vez.
  • O fluxo manual de criação de spec ("+ Nova spec") lê getA11yProjectOrigin() diretamente (sem abrir modal).
  • Editável a qualquer momento via modal "Sobre o hac" → botão "Trocar".
  • Resetada ao "Limpar Cache" (ver seção 1).

Exceção deliberada: "Reescanear" dentro do resumo da Detecção Automática. rescanA11yBatchArea() não chama ensureA11yProjectOriginThen — ela zera pending.declaredOrigin e força a modal de origem a reabrir manualmente, mesmo com hacData.projectOrigin já definido. Decisão explícita: a lib pode ter mudado entre uma varredura e outra, então cada Reescanear pergunta de novo qual plataforma usar para aquela passada específica — a resposta não sobrescreve hacData.projectOrigin (só o campo local usado para retropreencher Título/Decorativo daquela varredura). Não é bug — é a única ação que legitimamente pergunta de novo.

Fase 4 (2026-09-04): escolha movida para a Home, em 2 etapas. Motivo: o modal educativo "Entendendo as categorias" não sabia a origem no momento em que podia ser aberto, e resolvia isso misturando texto de web e mobile no mesmo parágrafo. A Home ganhou 2 telas internas (#a11y-home-step-origin/#a11y-home-step-summary, alternadas por _renderA11yHomeOriginPicker): a primeira, objetiva, só com descrição curta do plugin + escolha Web/Mobile; a segunda, só depois de escolhida, com o resumo do fluxo (os 3 cards que antes eram todo o conteúdo da Home) e o botão "Começar". Arquivo já configurado pula direto pra segunda etapa. ensureA11yProjectOriginThen continua como fallback para arquivos legados sem origem definida.

setA11yProjectOrigin passa a chamar _refreshUiForProjectOrigin() a cada mudança de origem — atualiza o picker da Home, o título do header secundário ("Documentando projeto Web/Mobile" no lugar do antigo "Acessibilidade" fixo), o filtro de categorias do seletor de Nova Spec, e o novo filtro do modal "Entendendo as categorias" (que passa a esconder "Estrutura da Página"/"Informações Adicionais" no mobile e alternar o texto das duas categorias com diferença real entre plataformas, nunca mais os dois ao mesmo tempo). Trocar a plataforma depois atualiza tudo in-place, sem sair da tela.

Com o título do header mais longo, os 3 ícones de ação (rever passo a passo, guia de categorias, recolher/expandir todos) foram recolhidos num dropdown "Mais ações" (toggleA11yMoreActionsMenu) — só "Voltar" e "Marcar Área" continuam diretos no header.

Fase 5 (2026-09-04): hacData.projectLib, granularidade real por lib. O hac já reconhece 4 libs de produto distintas (refs/_manifest.json): web-angular-react (legado), super-dsc-web (nova, coexiste com o legado na mesma tela), super-app (mobile), dsc-android (mobile) — e o matching de componente já calcula essa identidade granular (match.sourceLib, _resolveDscComponentA11yMatch). projectLib ('web-angular-react' | 'super-dsc-web' | 'super-app' | null) expõe isso na UI sem substituir projectOrigin, que continua sendo a fonte de verdade da lógica binária madura (formulário mobile/desktop, selos, filtro de categorias). setA11yProjectLib grava os dois juntos sempre, via A11Y_LIB_TO_ORIGIN. Home lista as 3 libs escolhíveis (dsc-android reconhecida mas fora da escolha); header mostra o rótulo exato; onboarding ganha uma 2ª camada específica por lib (ONBOARDING_TOOLS['lib-*'], onboarding.js), disparada uma vez logo após a escolha.

4. needsReview

Campo boolean em cada spec. Hoje só é setado true em um cenário real: migração retroativa de "Elementos e Imagens" mobile pré-sub-variantes, quando a heurística de inferência cai no fallback mais arriscado (não consegue determinar a variante com confiança).

Toda spec criada pelo wizard de revisão individual (Detecção Automática) nasce sempre com needsReview: false, mesmo que a detecção original tivesse baixa confiança — a revisão humana item a item já substitui qualquer necessidade de sinalização automática. O conceito de "confiança alta/baixa" foi removido da UI (badges de confiança no resumo do lote) pela mesma razão: com revisão individual obrigatória, a distinção virou ruído sem efeito prático.

5. Elementos e Imagens mobile — 3 sub-variantes

Estrutura real do componente Figma [a11y mob] Box specs leitor de tela (variante "Conector = Elementos e imagens"), com property Variante (VARIANT): componente | link | texto alternativo.

  • Componente: Descrição/Nome acessível/Dica Leitor de Tela/Observação (toggles opcionais) + Link do Componente (sempre visível). O dropdown de 64 nomes reais de componentes DSC vem pré-selecionado automaticamente quando o dscComponentName resolvido bate por nome exato com um dos 46 nomes que têm nodeId conhecido (gerando também a URL de deep-link); os outros 18 nomes divergem editorialmente entre a lib real e a lista curada — ficam manuais ("Personalizado"). Sempre que o <select> aponta para qualquer opção diferente de "Personalizado", o campo de texto vira readOnly, com hint visual de cadeado — só fica editável quando "Personalizado" está selecionado.
  • Link: Descrição fixa e travada ("Identificar como link e anunciar que o link abre uma nova janela..."), Nome acessível/Observação opcionais.
  • Texto Alternativo: Descrição livre obrigatória (alt-text real), Observação opcional.

O campo Nome acessível foi consolidado: existia como toggle duplicado dentro de "Campos exclusivos mobile" e também como o campo "Label" do topo do formulário — ambos alimentavam o mesmo accessibilityLabel. O toggle mobile foi removido; "Label" do topo é a única fonte, e seu valor liga o toggle BOOLEAN real do componente. Mesmo padrão aplicado ao desktop/web: o checkbox dinâmico "Nome Acessível" (renderizado a partir da property BOOLEAN real do componente DSC selecionado) duplicava o campo "Label" sempre visível no topo — foi filtrado fora da lista de toggles renderizados, e o payload passou a injetar { key: 'nomeAcessivel', value: label } automaticamente a partir do Label do topo, para todo componente. Isso é seguro porque o backend já ignora silenciosamente properties dinâmicas sem toggleDef correspondente no componente.

Bug real corrigido: o toggle BOOLEAN ligava corretamente, mas o TEXTO da sub-instância continuava sendo o placeholder publicado da lib, nunca o valor real digitado — mesmo bug nos outros 3 campos desta variante. Causa raiz: o preenchimento buscava um TEXT node cujo nome de CAMADA batesse com um regex — mas a árvore real não tem TEXT nodes com esses nomes: cada campo é uma INSTANCE aninhada cujos dois TEXT filhos se chamam sempre "Label"/"Text" (genéricos). O conteúdo real é uma component property de texto própria de cada sub-instância. Correção: novo helper _findNestedInstanceByName acha a INSTANCE pelo nome dela (não pelo TEXT filho), e o preenchimento passou a usar setProperties na property Texto da sub-instância.

Filtro por origem

O matching de categoria usa dois Maps separados por plataforma (_dscFrameToA11yMapWeb/_dscFrameToA11yMapMobile). A resolução de match já sabe a origem do componente antes de consultar o mapa de categoria — consulta só o mapa da própria plataforma. Um componente que só bate por nome na lib da plataforma errada corretamente vira isUnmapped: true em vez de herdar uma categoria da lib errada.

Princípio: componente real sempre, procedural só como último recurso

A importação de componente real lança exceção em qualquer ponto de incerteza; o chamador trata como "cai no card procedural" só para uma whitelist fixa de razões esperadas. Qualquer outra falha gera erro visível ao designer (nunca falha silenciosa).

Preenchimento fino de campos internos: implementado para as 3 categorias cobertas pelo wrapper mobile (Elementos e Imagens, Títulos, Elementos Decorativos). Títulos e Elementos Decorativos só expõem uma property Observações (BOOLEAN) internamente — Descrição e Notas de Código são conteúdo fixo hardcoded na lib publicada, sem property exposta (limitação real da lib, confirmada via API).

"Componente DSC" como link de referência

O campo read-only "Componente DSC" no cabeçalho do modal vira um link clicável para o componente real na lib do Figma, só quando é possível montar um deep-link com confiança via um dicionário de 46/64 nomes que existe só para a lib mobile (extraído com containingFrameNodeId) — os JSONs das libs web não têm esse campo. Specs de projeto web nunca ganham link (cai no texto puro), e mesmo em mobile os nomes sem match seguro ficam só como texto.

"Outro" (componente não mapeado)

Quando um componentKey real é encontrado sem categoria de a11y catalogada (ex: [dsc] Card, [dsc] Tooltip), a Detecção Automática sugere "Outro (nome do componente)" — sinaliza que aquele componente precisa ganhar uma spec formal na lib, mas hoje não existe processo institucional automatizado que capte esse sinal; é só um rótulo visível na tela de revisão do designer.

Curadoria pontual de matching a partir de dsc-structural-review.json (2026-09-09)

dsc-structural-review.json reúne 87 candidatos de confiança baixa revisados estruturalmente (árvore real de filhos via MCP do Figma, não só nome). 4 achados dessa curadoria já preenchida foram aplicados diretamente nos JSONs de mapeamento consumidos em runtime (build-dsc-a11y-mapping.cjs não foi alterado — os 2 arquivos gerados foram editados pontualmente):

  • [dsc] Alert (lib web-angular-react): estava em semMatch (match: null) apesar de ter papel ARIA (role="alert") muito próximo de "snackbar". Movido para baixaConfianca com match.shortName = "snackbar" — confiança baixa (não alta) porque a aproximação é semântica, não literal pelo nome. Não existe [dsc] Alert exato nas outras 3 libs (só variações diferentes como [dsc] Card Alert, que é outra categoria, e nomes de ícone como shield-alert/message-alert, corretamente filtrados como ruído) — a correção não foi replicada nelas.
  • [dsc-tc] Avatar Hero (lib super-app): já mapeado como imagem/confiança baixa; a revisão estrutural confirmou que é um componente composto (avatar + nome do usuário + mensagem de boas-vindas) que deve ser entendido como "imagem acompanhada de cabeçalho". shortName mantido (imagem continua a categoria correta), só a reason do match foi reescrita para registrar essa nuance.
  • [dsc-ts] Screen Input Money e [dsc-ts] Screen Item Select List (lib super-app): eram tratados como match único de baixa confiança (inputs e listas, respectivamente), mas são templates de tela completos (teclado virtual + campo de valor monetário; modal de busca + lista + ações), não componentes atômicos. Removidos de baixaConfianca e movidos para semMatch (match: null) — deixam de aparecer como sugestão enganosa de categoria única na Detecção Automática. Decompor esses templates em subcomponentes reais fica fora de escopo desta correção pontual (não implementado).

As demais 83 entradas de dsc-structural-review.json (80 que confirmam o match atual sem mudança de categoria, mais os candidatos não citados acima) não foram alteradas nesta correção.

Ícones decorativos dentro de componentes já reconhecidos (2026-09-09)

Regra original: ao encontrar uma INSTANCE já resolvida com a11yCategory (_hasResolvedDscMatch, code.js), a recursão da Detecção Automática parava por completo — os filhos internos (glifos, textos, ícones decorativos embutidos) eram tratados como parte da MESMA unidade já documentada, evitando detecções concorrentes e fragmentadas (bug real corrigido em 2026-09-04: um Badge aninhado num "[dsc] Value Section" virava item separado e duplicado do componente pai).

Caso real que expôs a lacuna: [dsc-tc] Actions - Button Row (mobile, Super App) — cada botão tem um ícone interno que precisa virar spec própria de Elemento Decorativo, mas ficava completamente invisível pela regra acima. Corrigido de forma cirúrgica, sem reabrir o bug original: quando o componente pai já resolve (_hasResolvedDscMatch), a recursão passa a descer só 1 nível dentro dele (parâmetro parentComponentMatch em _extract) — e nesse modo restrito, só um filho classificado como icons pela heurística já existente (_isIconGroupContainer/isIcon) é aceito como item; qualquer outra categoria (texto solto, outra INSTANCE de componente DSC, sub-frame estrutural) é descartada, e a recursão nunca desce mais fundo que esse 1 nível. O item resultante ganha parentComponentMatch no dado bruto (contexto de qual componente pai ele veio) — já sobrevive ao pipeline do frontend via spread genérico (_collectA11yDetections, mesmo padrão de treeOrder), consumo visual (ex. "ícone dentro de: X" na revisão) ainda não implementado.

Por que não uma lista curada de componentes "compostos": os arquivos refs/*.json (gerados por fetch-design-refs.cjs via REST API) só trazem metadados planos (key/nome/containingFrame) — nunca árvore de filhos (confirmado lendo o script: só consulta /components, /component_sets, /styles, /variables/local, nunca /nodes). Uma lista estática de "estes componentes podem descer +1 nível" seria baseada só em suposição de nome, não em estrutura real. A decisão é feita em runtime, pela árvore real do arquivo do designer, no momento do próprio scan — cobre automaticamente qualquer componente composto (Header com ícones de ação, List Item com ícone de status), sem lista de nomes para manter.

Ordem de Tabulação — nome exibido, não a mecânica: o caso trouxe também uma pergunta conceitual — o item certo da Ordem de Tabulação continua sendo o componente inteiro (o botão, nunca o ícone interno isoladamente; um elemento focável = 1 parada de Tab, regra WCAG real). O que mudou foi só o TEXTO mostrado na revisão do Mapeamento Automático: antes, generate-tab-order-from-layers usava sempre o nome da CAMADA do Figma (ex. "Button 1"); agora, novo helper _findVisibleLabelText(node, depth) busca o primeiro TEXT visível dentro do componente (recursão rasa, até 3 níveis) e usa esse texto como nome do item quando existir — o "nome acessível" real que um leitor de tela anuncia ao chegar naquele botão. Cai no nome da camada como fallback quando não há texto (ex. um Icon Button puro, só ícone). Não afeta em nada QUANTAS paradas a Tabulação gera.

7. Fluxos de criação de spec

Manual ("+ Nova spec")

Seleção de elemento → checagem de vínculo da lib → escolha de categoria → formulário. a11yOrigin vem de getA11yProjectOrigin() (configuração já definida do projeto).

Detecção Automática (wizard sequencial de revisão)

Ponto de entrada migrado pra tab Leitor de Tela (2026-09-04-g): antes, a escolha "Detecção Automática vs. Manual" era feita no PRÓPRIO modal de criação da Área (#a11y-area-modal, radio "Como documentar esta área?"), disparando a varredura automaticamente no momento de marcar a área. Isso saiu do modal — "Marcar Área" agora só cria a área, sem escolha nem varredura. O Mapeamento Automático virou um botão ("ou usar Mapeamento Automático") dentro da tab Leitor de Tela, ao lado do fluxo manual de criar spec — reaproveita openA11yPostAreaDetectModal(area) (já existia, usado antes só pra retomar/reescanear uma área já documentada) via um novo wrapper _startA11yMappingFromLeitorTab(areaId). autoDetect não é mais enviado por confirmA11yArea/create-a11y-area.

Todo item detectado — sem exceção de categoria — passa por configuração/confirmação individual antes de virar spec real:

  1. Tela de entrada: escolher a Área de destino (ou já vir com a área corrente pré-selecionada, quando disparado pelo botão da tab Leitor de Tela), ver contagem agregada.
  2. Um snapshot em memória é montado (nunca persistido, nunca escreve na fonte bruta de detecções).
  3. Cada item abre o formulário normal, com indicador de progresso "Item N de M", botões "Focar" (destaca o elemento no canvas) e "Descartar" (pula sem criar spec).
    • Correção de categoria durante a revisão: um ícone de editar permite trocar a categoria sugerida inline, reabrindo o formulário em estado default para a nova categoria — sem migração de campos entre categorias diferentes. Existe só durante o wizard.
    • Navegação livre + campo de posição editável: a revisão não é mais estritamente sequencial. Botões Voltar/Avançar navegam sempre por posição na fila; um campo numérico central permite pular diretamente para qualquer item. Reabrir um item confirmado mantém o formulário visível mas o botão "Aplicar" vira "Documentado" (desabilitado) — nunca duplica a spec. Reabrir um item descartado reabre totalmente editável.
    • Foco automático no canvas ao trocar de item: a cada troca de item, a viewport centraliza/destaca o elemento correspondente automaticamente.
  4. confirmA11ySpec() no modo wizard força needsReview: false e aguarda a resposta real do backend antes de avançar.
  5. Cancelar a revisão preserva as specs já confirmadas; itens ainda não vistos voltam para "Não Documentados".
    • Distinção Cancelar explícito vs. fechamento acidental: fechar via X/Esc oferece retomada (toast com botão "Continuar revisão", que dispara um novo scan da área e retoma o wizard); clicar em "Cancelar" explicitamente não oferece essa opção.

8. Ordem de Tabulação

Organização em Sections dedicadas

O hac usa duas Sections distintas no canvas:

  • "hac — Especificações de Acessibilidade": Áreas Marcadas + specGroups de todas as categorias.
  • "hac — Ordem de Tabulação": só as cópias de frame criadas para revisão de tabulação (uma por Área Marcada já trabalhada) e os selos numerados dentro delas. Separada da Section de specs porque dezenas de selos/conectores de spec se misturariam visualmente, no painel de Layers, com cópias inteiras de tela.

Section versionada — reconhecimento de documentação existente (2026-09-03)

Motivo de negócio: um designer pode abrir um arquivo que outro designer já documentou por completo. Na prática isso quase sempre significa duplicar o frame principal e especificar essa cópia — não "documentar por cima" da estrutura antiga. Sem tratamento, a nova Área cairia dentro da MESMA Section única, misturando visualmente (no painel de Layers) o handoff antigo com o novo.

O nome da Section de specs deixou de ser só a constante fixa A11Y_SECTION_NAME — hacData.activeSectionName guarda o nome ATIVO escolhido pelo designer nesta sessão (mesmo padrão de campo simples de configuração de projeto que projectOrigin; null resolve pro nome fixo original, sem nenhuma migração). getA11yActiveSectionName()/ setA11yActiveSectionName() (accessibility.js) são os helpers análogos a getA11yProjectOrigin()/setA11yProjectOrigin().

_getOrCreateA11ySection(sectionName)/_reparentIntoA11ySection(node, sectionName) (code.js) passam a aceitar o nome como parâmetro, com A11Y_SECTION_NAME como default quando omitido/vazio. _getOrCreateTabOrderSection/_reparentIntoTabOrderSection aplicam o MESMO sufixo de versão à Section de Ordem de Tabulação (_extractA11ySectionVersionSuffix), mantendo as duas Sections de uma mesma geração de documentação juntas e coerentes. Os handlers que criam nós dentro da Section (create-a11y-area, create-unified-spec via opts.sectionName, start-tab-order-copy, generate-tab-order-from-layers, apply-tab-order-to-canvas) recebem sectionName no payload, com fallback pro nome fixo se ausente. _collectA11yOccupiedBounds (cálculo de "faixa livre" pra novas cópias de Ordem de Tabulação) varre TODAS as Sections com o prefixo base existentes na página — não só a ativa — pra nunca sobrepor documentação de handoffs antigos.

_computeNextA11ySectionName() (code.js) varre as Sections já existentes na página com o prefixo base, extrai o sufixo de versão de cada uma (sem sufixo = v1 implícito, a Section original) e devolve o próximo número livre ("hac — Especificações de Acessibilidade v2", v3...).

Fluxo de reconhecimento: novo handler get-a11y-documentation-status, consultado por openA11yAreaModal toda vez que o modal "Marcar Área" abre (fonte de verdade é sempre o CANVAS, não só o array a11yAreas em memória — cobre Section de uma sessão anterior do plugin). Se houver documentação existente, o mesmo modal a11y-area-modal (sem modal novo) revela um bloco de aviso com o nome/contagem da Section atual e dois botões: "Continuar na Section atual" (default, comportamento idêntico a antes) e "Iniciar nova Section" (a troca real de hacData.activeSectionName só se efetiva ao confirmar a área — cancelar o modal não deixa a Section ativa trocada silenciosamente). Arquivo vazio (nenhuma Área ainda) = aviso nunca aparece, modal funciona exatamente como antes desta feature.

Fora de escopo (decisão explícita): restaurar/reverter pra uma Section antiga como ativa; comparar/navegar entre gerações na listagem do plugin (a listagem principal de Áreas continua mostrando todas as áreas de todas as Sections juntas — a separação é só no canvas/Layers); aviso automático no boot do plugin.

Réplica da área criada e focada antes de marcar

Regra válida para os dois modos (manual e automático): a primeira coisa que acontece é clonar a Área Marcada para um espaço livre do canvas — sem sobrepor nada que já esteja na página. Logo após criar a cópia, o backend seleciona e foca a viewport nela, antes de o modal de revisão abrir — a área original acumula selos de outras specs e ficava visualmente confusa; o designer nunca marca em cima dela.

  • Modo manual: o designer clica fisicamente na CÓPIA (é o que está focado na tela). A tradução de id do clone para o id do original acontece antes de repassar ao frontend — é assim que a lista pendente sempre guarda ids do original.
  • Modo automático: a varredura por elementos interativos continua operando sobre o frame ORIGINAL; o backend devolve o mapa original↔clone junto com os itens encontrados.

Modo manual — sem bloqueio

Uma tentativa de bloquear cliques em elementos "não reconhecidos como acionáveis" foi implementada e revertida no mesmo dia: o reconhecimento automático falhava em casos reais visíveis (Icon Button de libs não mapeadas, cards customizados sem match) — travar o designer com base num reconhecimento incompleto causava mais dano do que benefício. Decisão final: qualquer clique no modo de captura entra direto na lista, sem checagem nem aviso.

Modo automático — só sugere itens reconhecidos

A varredura só coleta instâncias cujo componente resolve como interativo (button, checkbox, radio button, switch, inputs, paginator, stepper, tab group, accordion, breadcrumb, listas, link). É uma sugestão, não uma trava — o designer ainda revisa e edita a lista antes de aplicar.

Fluxo de revisão — selos reais incrementais (2026-09-03)

Nenhum selo é desenhado sobre os elementos reais em nenhum dos dois modos — sempre sobre a mesma cópia clonada já criada/focada no início do fluxo. Cada item que entra na lista pendente (clique manual ou item do scan automático) já desenha seu selo REAL na cópia na hora — nunca em lote, nunca redesenhando o que já existe. Apagar um item da lista apaga o selo real correspondente e renumera os remanescentes; reordenar por drag-and-drop renumera os selos reais existentes (nunca recria). O botão final do modal ("Concluir", antes "Aplicar no Canvas") não desenha mais nada — só persiste os itens já desenhados e fecha o modal.

Uma primeira tentativa de resolver esse mesmo problema via "selos fantasma" (preview semitransparente redesenhado do zero a cada mudança na lista) foi implementada e revertida no mesmo dia — funcionalmente correta, mas considerada complexa demais pelo ganho obtido.

Selo de ITEM de tabulação vs. selo de ÁREA — dois componentes diferentes

  • [a11y] Item Number (desktop) / [a11y mob] Número da tela (mobile) desenham um Connector dentro de cada variante de direção — fazem sentido para o selo de Área Marcada, que precisa de uma linha visual até a borda do frame/seção demarcada.
  • [a11y mob] Ordenação não desenha conector — os filhos de cada variante são só número + um ícone de seta encostando na borda do próprio selo. Não tem property de direção porque a posição é resolvida por x/y absoluto no código, não por variante do componente. É o componente certo para o selo de item de Ordem de Tabulação.

Desktop não tem um equivalente "sem conector" — é o único componente disponível na lib "Design Acessível" para selo numerado, e por isso segue reaproveitado tanto para Área quanto para item de tabulação nesse caso (assimetria real entre as duas libs, não um bug do plugin).

Modo manual volta a ser EM LOTE (2026-09-04-e) — reversão parcial e deliberada do modelo incremental

A vertical de acessibilidade trouxe uma proposta nova pro modo MANUAL (o automático não muda — ver abaixo): o designer seleciona a trilha inteira em sequência primeiro, e só ao confirmar no final a ordem é de fato criada/desenhada no canvas — voltando ao espírito do modelo anterior a 2026-09-03, mas SEM reintroduzir o bug que motivou aquela mudança.

O que muda: handleTabOrderSelectionChanged deixa de chamar _tabOrderDrawPendingBadge a cada clique — cada clique só empilha o item na lista pendente (canvasId: null, drawing: false) e mantém o highlight no canvas (highlight-tab-order-copy-node, não removido — é o único feedback visual enquanto a trilha está sendo montada, sem nenhum selo real ainda). applyTabOrderToCanvas (botão "Criar ordem de tabulação", renomeado de "Concluir") passa a ser async e é ELA quem desenha agora: itera a lista pendente inteira chamando await _tabOrderDrawPendingBadgeAwaitable(tempId) em sequência (mesmo helper já usado pelo scan automático, reaproveitado sem duplicar), mostrando progresso ("Desenhando N de M...") e só persiste em tabOrderItems os itens que de fato ganharam canvasId — itens que falharem ficam de fora, com aviso ao designer.

Por que isso não reintroduz o bug de 2026-09-03: aquele bug era "apagar/reordenar um item ANTES de confirmar não refletia nada no canvas", porque NENHUM selo existia até "Aplicar". Isso continua tecnicamente verdade aqui — mas agora é o comportamento ESPERADO, não um efeito colateral: o designer revisa/reordena a trilha inteira (a lista pendente já mostra a numeração correta) antes de qualquer selo nascer; o highlight a cada clique já indica visualmente o que foi selecionado. _tabOrderRenumberPendingCanvas nunca dispara renumber-tab-order-items durante essa montagem (nenhum item tem canvasId ainda) — só volta a mandar mensagem real pro backend no fluxo de "Atualizar" sobre uma ordem já aplicada.

O que NÃO muda: o modo AUTOMÁTICO ("Gerar Automaticamente", renomeado pra "Mapeamento Automático" — ver nota de nomenclatura abaixo) já desenhava em lote sequencial desde sempre (addTabOrderItemsFromLayers, mesmo _tabOrderDrawPendingBadgeAwaitable reaproveitado agora pelo manual) — zero mudança de lógica nele.

Hierarquia visual — manual vira o caminho primário, automático o secundário (pedido explícito da vertical: o automático deve ser a opção secundária de propósito, para que o designer aprenda o fluxo manual primeiro): "Iniciar Ordem de Tabulação" continua botão preenchido (primário); "Gerar Automaticamente"/"Mapeamento Automático" deixa de ser um botão outline do mesmo tamanho e vira um link/texto secundário e menor logo abaixo ("ou usar Mapeamento Automático") — nos dois lugares onde esse par de botões existe (_a11yWorkspaceTabTabulacao, e o bloco legado usado pelo bucket "Sem área").

Nomenclatura corrigida (2026-09-04-e/g): "Gerar Handoff Automatizado" virou "Mapeamento Automatizado" (modal de resumo do lote de detecção) e "Gerar Automaticamente" (Tabulação) virou "Mapeamento Automático" — motivo: nenhum desses fluxos produz um "handoff" pronto nem uma "geração" final — o resultado sempre passa por revisão do designer antes de virar spec ou ordem aplicada. Nunca usar "handoff"/"gerar" pra descrever esses fluxos automáticos daqui em diante.

Acrescentar itens a uma Ordem de Tabulação já existente (regra de produto)

O card de uma Área já documentada mostra "+ Adicionar item" (startTabOrderAddItemsFromCard), disponível junto da lista de itens já aplicados — tanto para uma ordem criada originalmente pelo fluxo manual quanto pelo Mapeamento Automático, sem distinção entre os dois. Regra de comportamento: um item novo (manual ou automático) SEMPRE entra como item ADICIONAL no fim da sequência atual, nunca substitui os itens já existentes — a única forma de sobrepor uma ordem já criada é apagar tudo e refazer do zero. Duas ações têm timing diferente: excluir (deleteTabOrderItem) aplica a renumeração no canvas IMEDIATAMENTE, sem precisar de nenhum clique extra; reordenar arrastando na lista só atualiza a posição em memória — o designer precisa clicar em "Atualizar" (updateTabOrderNumbering) para a nova numeração ser de fato recalculada e desenhada de volta no canvas (renumber-tab-order-items). Vale igualmente para projetos mobile e web — a origem do projeto (hacData.projectOrigin) só decide qual COMPONENTE de selo é desenhado (_createTabOrderBadge), nunca a mecânica de adicionar/editar/excluir itens, que é idêntica nos dois casos.

"+ Adicionar item" aceita shift+clique/marquise pra vários de uma vez (2026-09-08): antes desta correção, o botão só aceitava 1 elemento por vez — a 1ª contagem>0 do acumulador silencioso já disparava a leitura (handleTabOrderAccumulatedCountChanged), então um shift+clique em vários elementos de uma vez perdia todos menos o primeiro. Agora reaproveita a MESMA mecânica de acumulação silenciosa da captura inicial: o 1º clique em "Adicionar item" arma a captura, o botão vira "Concluir seleção (N)" com a contagem ao vivo, e só a leitura do acumulado (get-tab-order-accumulated-selection) acontece quando o designer clica nele de novo (finishTabOrderAddItemWait) — nunca automaticamente. O resultado é sempre ANEXADO ao final da lista pendente existente (handleTabOrderAccumulatedSelectionResult, branch de modal já aberto), nunca substituindo os itens já ali.

Bug real corrigido (2026-09-08): startTabOrderAddItemsFromCard era a única das 3 entradas do fluxo (manual do zero, Mapeamento Automático, e esta) que nunca declarava window._tabOrderDeclaredOrigin antes de desenhar o item novo — draw-tab-order-badge manda essa variável pro backend como a11yOrigin, com fallback 'web' quando não declarada. Em projeto mobile, todo item acrescentado por este caminho caía no fallback errado e importava o componente desktop "[a11y] Item Number" em vez do "[hac mob base]" que os demais itens da mesma ordem usam (sintoma real: selo visualmente diferente dos outros, alongado com conector). Em projeto web o bug nunca aparecia (o fallback coincidia com o componente certo), o que o manteve invisível até esta sessão. Corrigido lendo a origem real do projeto via ensureA11yProjectOriginThen (mesmo padrão já usado pelos outros 2 fluxos) antes de qualquer selo novo ser desenhado.

8a. Contrato do subsistema de clone/overlay (referência)

O que é isto: esta seção é uma REFERÊNCIA atemporal, não um histórico — reúne, num único lugar, o contrato que 4 features diferentes (Ordem de Tabulação, Swipe, Especificações/Leitor de Tela, Ficha de Handoff) já seguem hoje ao desenhar sobre uma CÓPIA de trabalho da Área, nunca sobre o frame original. O histórico de bugs reais que motivou cada regra abaixo está narrado na seção 8e; aqui fica só o contrato em si, para consulta rápida antes de tocar qualquer uma das funções citadas ou de adicionar um 5º consumidor.

Nota (2026-09-10, ver 8n): a partir desta data, dentro do Handoff Completo (Ficha), o CLONE de trabalho de Tabulação/Swipe/Leitor de Tela deixou de ser movido pra dentro da Ficha — só um snapshot (imagem) dele é inserido lá, via _snapshotCloneIntoFichaSection. O GRUPO-OVERLAY de marcadores continua sendo movido/reaproveitado normalmente pra dentro da Ficha, exatamente como descrito no resto desta seção — a única mudança de contrato é que overlay e clone podem agora viver em ramos DIFERENTES da árvore (overlay dentro da Ficha, clone preso pra sempre na Section de sessão), por isso _findCloneOverlaySibling não pode mais depender de parentesco (sibling.parent === clone.parent) — busca a página inteira.

Quem cria o clone, por feature:

  • Ordem de Tabulação — _createTabOrderCloneForArea.
  • Swipe — _createSwipePathCloneForArea (cache próprio, nunca compartilha clone/Map com Tabulação mesmo quando as duas features documentam a mesma Área).
  • Especificações (Leitor de Tela) — _createSpecCloneForArea.
  • Ficha de Handoff — _cloneAreaRootIntoFicha, a única das 4 que clona sempre a partir do frame ORIGINAL da Área, nunca de um clone de trabalho já existente (Tabulação/Swipe/Specs) — a Ficha é um artefato de export à parte, não uma continuação do canvas de trabalho.

Quem é dono de cada cache de clone ativo em memória (todos Map<areaId, nodeMap>, nunca uma variável global única — cada Área mantém seu próprio clone ativo por feature, sem colisão entre Áreas trabalhadas na mesma sessão):

  • _activeTabOrderCloneMaps — escrito por _resolveActiveTabOrderClone/_createTabOrderCloneForArea; lido por todo handler de Tabulação (draw-tab-order-badge, highlight-tab-order-copy-node, etc.) e também pela tradução de nodeId do Swipe (abaixo). Recriado quando o clone em memória não existe mais no canvas (.removed ou fora da página atual).
  • _activeSwipePathCloneMaps — mesmo padrão, escopo só da Trilha de Swipe.
  • _activeSpecCloneMaps — mesmo padrão, escopo só de Especificações.

Invariantes — checklist antes de mexer neste subsistema:

  • Overlay é sempre GROUP, nunca FRAME (_getOrCreateCloneOverlayGroup) — GROUP nunca tem clipsContent nem Auto Layout, o que o torna estruturalmente imune ao bug de conteúdo "vazando" sendo recortado.
  • Overlay nunca pode ficar vazio — mantém um retângulo seed permanente (visible=false, locked=true), nunca removido: um GROUP que perde o último filho é apagado automaticamente pelo Figma, levando junto qualquer artefato que ainda estivesse "dentro" dele do ponto de vista do JavaScript.
  • Nunca reparentar artefato para DENTRO do clone (selo de Tabulação, linha de Swipe, specGroup) — sempre no grupo- overlay IRMÃO do clone, via _reparentIntoAreaGroup.
  • Clone de INSTANCE sempre precisa de detachInstance() antes de qualquer appendChild — a Plugin API proíbe appendChild numa INSTANCE; comum quando a Área é marcada sobre uma tela publicada da lib "DSC | Super App".
  • layoutPositioning = 'ABSOLUTE' só pode ser setado DEPOIS que o node já tem parent com layoutMode !== 'NONE' — e precisa ser setado sempre que esse pai tiver Auto Layout, incluindo o próprio grupo-overlay (não só o artefato desenhado dentro dele: _setCloneOverlayGroupAbsolutePositioning). Achado mais recente deste subsistema: a Ficha de Handoff foi o primeiro consumidor cujo clone vive dentro de um pai com Auto Layout — sem este ajuste, o overlay participa do fluxo do Auto Layout como filho comum e se estica para cobrir a distância até coordenadas absolutas distantes (ex.: uma trilha de Swipe cruzando a tela original).
  • Tradução de nodeId entre clones de features DIFERENTES nunca é implícita — um id de node dentro do clone de Tabulação não existe no clone do Swipe (são clones distintos, sem id em comum). Quando uma feature reaproveita uma sequência mapeada por outra (ex.: "Gerar automaticamente" do Swipe usando a Ordem de Tabulação já feita), o id precisa ser traduzido de volta pro ORIGINAL antes de consultar o nodeMap da segunda feature (_resolveOriginalNodeIdFromTabOrderClone).
  • Toda leitura de posição usa absoluteBoundingBox/ absoluteRenderBounds, nunca node.x/ node.y crus quando o node pode estar dentro de uma Section ou de outro container — x/y são relativos ao PAI, não à página.
  • figma.on('close', ...) NUNCA pode remover um clone incondicionalmente (bug crítico corrigido 2026-09-10: fechar só a janela do plugin, sem fechar o Figma, disparava esse handler e apagava todo trabalho já confirmado — selos, trilha, specs). Os Maps de clone ativo (_activeTabOrderCloneMaps/ _activeSwipePathCloneMaps) guardam tanto uma captura recém- iniciada (overlay vazio, só o seed) quanto o clone de trabalho já confirmado — o handler de fechamento SEMPRE precisa checar _cloneOverlayHasRealContent(overlay) antes de decidir remover, e só descartar quando o overlay não tem nada além do seed. O cancelamento EXPLÍCITO do designer (delete-tab-order-draft-copy) é o único caminho que pode continuar removendo incondicionalmente.

Migração defensiva de overlay legado (_rescueLegacyOverlayNestedInsideClone, 2026-09-09): bug real reportado com print — ao "Inserir/Atualizar" a Ordem de Tabulação na Ficha, o grupo [Selos de Tabulação] ... aparecia ANINHADO DENTRO do clone [Ordem de Tabulação] ... no painel de camadas, em vez de irmão dele. Causa raiz confirmada (não suposição): entre a introdução do overlay-irmão e a rodada de correção anterior na mesma sessão, uma versão intermediária do código (_reparentIntoCloneAbsolute, introduzida e removida no mesmo commit) chegou a reparentar selos/trilha PARA DENTRO do clone — qualquer Área documentada nessa janela carrega esse overlay legado até hoje, sem nenhuma migração retroativa. _getOrCreateCloneOverlayGroup e _moveActiveCloneIntoFichaSection só procuravam o overlay como IRMÃO do clone; contra um overlay legado aninhado por dentro, essa busca sempre falhava — _moveActiveCloneIntoFichaSection então movia só o clone (levando o overlay legado junto, agarrado por dentro, pra dentro da Ficha), e _getOrCreateCloneOverlayGroup criava um segundo overlay novo e vazio do lado de fora, deixando os selos antigos órfãos dentro do clone. Corrigido com uma função compartilhada pelos 3 fluxos (Tabulação/Swipe/Leitor): busca recursiva por um GROUP marcado com o pluginDataKey esperado em qualquer profundidade dentro do clone e, se achar, resgata pra fora via _reparentIntoAreaGroup (mesma compensação de x/y por diferença de bounding box já usada no resto do subsistema) ANTES de prosseguir com a lógica normal de busca-por-irmão/move/criação. Idempotente: clones já corrigidos (overlay já irmão, ou nunca teve overlay algum) não encontram nada a resgatar e seguem o caminho de sempre.

Réplicas de trabalho nascem AO LADO do original, não mais abaixo (2026-09-09): _findFreeTabOrderCopyPosition decidia sempre y = oy + oh + gap (empurra pra baixo ao colidir) — trocado por x = ox + ow + gap, mesma altura do original (y = oy), empurrando mais pra DIREITA ao colidir em vez de mais pra baixo. Motivo: o designer pode começar a documentar por qualquer um dos 3 blocos (Swipe, Leitor de Tela, Tabulação), em qualquer ordem — cada um pode precisar criar uma réplica NOVA (quando não há uma já reaproveitável pela Área, reaproveitamento que não muda aqui) e ela precisa nascer num espaço livre sem sobrepor nada que já exista, independente de qual bloco foi criado primeiro. A fonte de colisão continua _collectA11yOccupiedBounds() + _rectsOverlap, sem nenhuma reimplementação — só a direção de avanço mudou. Confirmado por leitura completa de _collectA11yOccupiedBounds: ela já soma, recalculado a cada chamada, o bounding box do fichaFrame inteiro (Auto Layout que cresce conforme seções/cards entram) como um bloco ocupado único — cobre também os cards de specs do Leitor de Tela dentro dela sem precisar de um bound por card (mesmo princípio conservador já usado pra Grupos de Área/Section de sessão: nunca soma o container vazio de antemão, sempre o tamanho real no momento da chamada). Nenhuma lacuna real encontrada nessa função — não foi alterada.

Ficha reparentada de volta pra Section principal se estiver fora dela (2026-09-09): bug real — a Ficha podia aparecer FORA da Section de sessão ("hac — Especificações de Acessibilidade — ..."). Causa: _createOrGetFichaFrame só chamava _reparentIntoSection no caminho de CRIAÇÃO do frame; uma Ficha já existente (existing, achada por _findFichaFrameForArea) era sempre devolvida como estava, sem nenhuma checagem de que ainda vivia dentro da Section — qualquer Ficha criada antes dessa chamada existir no código, ou desalinhada por outro motivo, ficava fora para sempre, mesmo depois de repetidos "Atualizar". Corrigido: ao resolver uma Ficha já existente, sobe pela árvore de ancestrais checando hacSessionSection === 'true'; se nenhum ancestral tiver essa marca, reparenta agora, com a mesma função já usada na criação (idempotente e segura de chamar de novo quando já está correta).

Antes de adicionar um 5º consumidor deste subsistema: confirme explicitamente se o pai do clone terá Auto Layout (se sim, _setCloneOverlayGroupAbsolutePositioning já cobre — só chamar) e se existe algum clipsContent novo no caminho entre o clone-raiz e onde o artefato vai nascer. Não assuma que as premissas dos 4 consumidores atuais bastam — cada um dos 7-8 bugs reais que motivaram este contrato (histórico completo em 8e) só apareceu quando um consumidor novo violou uma premissa que os anteriores nunca tinham testado.

Candidata futura, ainda não implementada: as 3 funções de tradução de nodeId hoje quase idênticas (_resolveOriginalNodeIdFromTabOrderClone, _resolveTabOrderCloneSelectionToOriginalId, _resolveSwipePathCloneSelectionToOriginalId) poderiam virar uma única abstração parametrizada por feature — cada uma resolve hoje, de forma independente, o mesmo problema geral de "id no clone → id no original". Registrado aqui como oportunidade, não como pendência bloqueante.

Swipe — histórico de 3 versões na mesma sessão (2026-09-04)

O desenho de Swipe mudou de conceito 3 vezes seguidas na mesma sessão, por rodadas de correção de entendimento com o usuário. Registrado aqui para não repetir a confusão em trabalho futuro:

  1. V1 (a versão original): pipeline DUPLICADO (não generalizado) de Ordem de Tabulação — cópia rascunho por área, captura sequencial de elementos DENTRO da mesma área, selos numerados via [a11y mob] Ordenação. Descartada porque o usuário esclareceu que Swipe não é sobre ordem de elementos dentro de uma tela.
  2. V2: conexão ENTRE exatamente 2 Áreas Marcadas diferentes, escolhida por dropdown (hacData.a11ySwipeFlows[], {sourceAreaId, targetAreaId}), desenhando uma linha reta única entre os dois selos. Descartada porque o usuário esclareceu (com imagem de referência real) que o modelo correto suporta N pontos em sequência, não só 2.
  3. V3 (atual): trilha direcional multi-ponto — ver seção 8d.

A V1 e a V2 foram removidas por completo (schema, backend e frontend) em cada correção — não há código de nenhuma das duas mantido "por via das dúvidas".

8d. Swipe V3 (2026-09-04): trilha direcional multi-ponto

Swipe é uma trilha com N pontos em sequência, desenhada como uma única linha direcional contínua com setas no canvas — não mais ordem de elementos dentro de 1 área (V1) nem conexão fixa entre 2 áreas (V2). Pontos NÃO são restritos a Áreas Marcadas — podem ser qualquer elemento/frame clicado no canvas, mesma liberdade que a Ordem de Tabulação já tem.

Dois modos de captura:

  1. Sequencial manual: clique nos pontos em ordem no canvas — mesmo modelo EM LOTE que Tabulação (seção 8, "Modo manual volta a ser em lote"): cada clique só empilha na lista pendente + highlight, sem desenhar nada; a trilha real só nasce ao confirmar "Criar trilha de Swipe".
  2. Seleção múltipla de uma vez: shift+clique/marquise seleciona vários pontos simultaneamente. Como a Plugin API não expõe ordem de clique para seleção múltipla, a ordem é resolvida por _orderNodesInZigzagReadingOrder — a MESMA função já usada pelo Mapeamento Automático de Tabulação (seção 8), movida de dentro do closure de figma.ui.onmessage para escopo top-level (corpo inalterado) para que o listener de selectionchange também possa chamá-la. Sem "Mapeamento Automático" próprio para Swipe nesta entrega (fora de escopo — extensão futura, se pedida).

Schema: hacData.a11ySwipePaths[] substitui a11ySwipeFlows[] (removido por completo) — {id, points: [{nodeId, nodeName}, ...], areaId, createdAt}. Aditivo, sem bump de _schemaVersion (mesmo precedente de todo campo novo desta sessão). Uma área tem no máximo 1 trilha — substituição completa ao recriar.

Geometria (code.js): _buildSwipePathConnection(nodes) desenha N-1 segmentos em sequência (cada um com sua própria seta, calculada por ângulo do segmento, mais um ponto de origem), agrupados com figma.group(). Linha mais grossa e marcada que a versão anterior (pedido explícito do usuário): strokeWeight 4 (era fino/padrão antes), cor cyan #0891B2 de destaque. Section própria — a constante A11Y_SWIPE_FLOW_SECTION_NAME manteve o NOME (decisão pragmática do agente pra não tocar todas as referências), mas o VALOR mudou pra 'hac — Trilhas de Swipe' — o nome da constante em si ficou levemente enganoso (sugere "fluxo", que era o conceito da V2), mas não é um bug: nenhum lugar do código compara contra um literal hardcoded divergente, só contra a própria constante.

Resolve de propósito o achado de QA da V2 (dessincronia canvas↔dado): o handler insert-swipe-path desenha a trilha NOVA primeiro e só remove a trilha ANTIGA depois de confirmar sucesso — nunca o contrário. Se o desenho novo falhar, a trilha antiga permanece intacta no canvas e no dado, em vez de ficar "mentindo" que existe uma trilha que não está mais lá.

Modal de revisão (views/modals.html): #a11y-swipe-path-review-modal, estrutura análoga ao #a11y-tab-order-review-modal (lista pendente + drag-and-drop). Desde 2026-09-09 também tem botão "Adicionar ponto" (ver seção 8i) — texto acima desatualizado corrigido: não é mais verdade que o modal não tenha esse botão.

Ficha de Handoff, seção Swipe: mostra a trilha completa em ordem ("1. X → 2. Y → 3. Z"), não mais "leva para X" (texto da V2).

Limitação aceita conscientemente: ocultar a Área via "Ocultar/Mostrar no canvas" não afeta a trilha de Swipe desenhada (ela não é uma cópia de frame por área como Tabulação, é uma única linha/setas) — mesma decisão já tomada na V2, documentada explicitamente no código (toggleAreaGroupVisibility).

8i. Editar a Trilha de Swipe já criada (2026-09-09)

Até esta entrega, uma Trilha de Swipe já criada só oferecia duas ações no card da tab "Swipe": "Refazer trilha de swipe" (reabre a captura inteira do zero) ou "Remover trilha" (apaga tudo). Não havia como adicionar 1 ponto, remover 1 ponto específico, ou reordenar sem recomeçar a captura inteira — diferente da Ordem de Tabulação, que já tinha edição item-a-item ("Adicionar itens" numa área já documentada, seção 8/8b). Esta entrega dá à Trilha de Swipe o mesmo nível de edição, inclusive quando ela nasceu do atalho "usar a Ordem de Tabulação já mapeada".

A mecânica de edição (drag-and-drop, remover por item, destacar ao clicar) já existia no modal de revisão — só nunca era aberta a partir de uma trilha JÁ SALVA. openSwipePathEditMode(areaId, targetNodeId) (novo, accessibility.js) resolve a trilha salva em hacData.a11ySwipePaths, popula window._swipePathPendingList a partir de existingPath.points (mesmo formato de startSwipePathFromTabOrder) e chama openSwipePathReviewModal() — sem nenhum caminho novo de desenho: confirmar ("Salvar alterações") cai no mesmo applySwipePathToCanvas → insert-swipe-path que já existia, que sempre apaga a trilha antiga inteira e redesenha do zero a partir da lista enviada (a trilha é 1 grupo indivisível no canvas, sem id persistido por segmento/ponto — qualquer edição, mesmo de 1 ponto, sempre foi "redesenhar tudo", igual ao "Refazer" de sempre).

Botão "Editar pontos" no card já-criado (visível junto do resumo "Trilha de Swipe (N pontos)"), estilo secundário (mesmo padrão do botão "Atualizar" de outras abas de trabalho).

Modal distingue criar de editar via window._swipePathEditingExisting (novo flag, default false): openSwipePathReviewModal() troca 3 textos por JS conforme o flag — título ("Trilha de Swipe" vs. "Editar Trilha de Swipe"), instrução, e texto do botão de confirmar ("Criar trilha de swipe" vs. "Salvar alterações"). Os 3 elementos ganharam ids endereçáveis (#a11y-swipe-path-review-title-text, #a11y-swipe-path-review-instruction, #a11y-swipe-path-review-confirm-text) — o botão de confirmar em si (#btn-swipe-path-apply) passou a ter um <span> interno em vez de textContent direto, porque applySwipePathToCanvas/handleSwipePathCreateFailed já reescreviam o texto do botão durante o processamento ("Desenhando trilha…") e precisavam continuar fazendo isso sem perder o rótulo correto do modo. O flag é resetado em cancelSwipePathReview e handleSwipePathCreated para nunca vazar entre sessões do modal.

"+ Adicionar ponto" dentro do modal (sempre visível, não só no modo edição — também útil ao revisar uma trilha recém-capturada antes da 1ª confirmação). Espelha "+ Adicionar item" de Tabulação (startTabOrderAddItemsFromCard/startTabOrderAddItemWait), com uma diferença crítica de backend: start-swipe-path-mode SEMPRE clona um frame novo do zero (_createSwipePathCloneForArea remove qualquer cópia anterior da área antes de clonar) — certo para "Iniciar/Refazer trilha de swipe" (captura do zero), mas catastrófico para "+ Adicionar ponto" numa trilha em edição: chamá-lo apagaria a cópia com o trabalho de revisão em andamento. Por isso esta entrega separa em dois handlers novos:

  • resolve-swipe-path-clone (código.js) — espelha resolve-tab-order-clone: reconhece/reaproveita o clone existente via _resolveActiveSwipePathClone (só recria se genuinamente sumiu), SEM abrir escuta de seleção. Responde swipe-path-clone-resolved.
  • start-swipe-path-listen-only — liga _swipePathModeActive = true (contagem ao vivo/highlight) sem clonar nada. start-swipe-path-mode continua sendo o único caminho que clona (fluxo de captura do zero).

startSwipePathAddPoint() chama resolve-swipe-path-clone primeiro; só na resposta de sucesso (handleSwipePathCloneResolved) é que a captura é de fato armada (_swipePathStartAddPointWait, que dispara start-swipe-path-listen-only e transforma o botão em "Concluir seleção" — aceita shift+clique/marquise para vários pontos novos de uma vez, mesmo padrão de startTabOrderAddItemWait).

handleSwipePathAccumulatedSelectionResult passou a diferenciar "captura inicial" de "+ Adicionar ponto" pelo modal já estar visível ou não (mesmo critério de handleTabOrderAccumulatedSelectionResult): modal fechado substitui _swipePathPendingList do zero (comportamento inalterado de "Iniciar"/"Refazer"); modal já aberto ANEXA os pontos novos ao final da lista existente, sem duplicar renderização/abertura.

8c. Ficha de Handoff (2026-09-04): módulo apartado, inserção incremental por seção

Implementa o artefato que ficara "fora de escopo" nas duas entregas anteriores: a Ficha de Handoff é um frame no canvas do Figma, por Área Marcada, montado a partir de uma imagem de referência real trazida pelo usuário (ficha "Handoff de acessibilidade — Ordem de tabulação e Leitor de Telas [Super App]": legenda + telas com selôs numerados + cards de especificação por selo, organizados em seções lado a lado). É um artefato de EXPORT destinado ao time de desenvolvimento — nesta 1ª versão, o formato de saída é o próprio frame no Figma (o dev acessa pelo link do arquivo ou usa o "Export" nativo do Figma para PNG/PDF; o plugin não gera arquivo externo).

Modelo de inserção incremental (decisão do usuário, mudou o desenho original do dashboard): não existe um botão único "Gerar handoff" que monta tudo de uma vez. Em vez disso, cada uma das 3 abas de trabalho — Tabulação, Swipe, Leitor de Tela — tem seu próprio botão "Inserir na ficha", que insere/substitui só a seção correspondente dentro do frame da Ficha daquela área. O botão vira "Atualizar ficha" assim que aquela seção já foi inserida — estado persistido em hacData, não inferido do canvas a cada render:

a11yAreas[i].handoffFicha = {
  frameId: null,           // id do frame da Ficha no canvas, quando existe
  sections: {
    tabulacao: { insertedAt: null, itemCount: 0 },
    swipe:     { insertedAt: null, itemCount: 0 },
    leitor:    { insertedAt: null, specCount: 0 },
    review:    { insertedAt: null, itemCount: 0 }, // 4º bloco, ver seção 8f
  },
}

Campo aditivo, sem bump de _schemaVersion (mesmo precedente de a11ySwipePaths/projectOrigin — seção 1); áreas antigas sem esse campo são tratadas defensivamente (area.handoffFicha?.sections?.[key]) em todo ponto de leitura.

Módulo apartado (palavras do usuário, reforçadas explicitamente): frontend isolado em src/plugin/modules/handoff-ficha.js (arquivo próprio, não espalhado dentro de accessibility.js), tudo prefixado _ficha para não colidir por nome com o resto — _fichaInsertSection, _fichaHandleSectionInserted/ _fichaHandleSectionInsertFailed, _fichaViewOnCanvas, _fichaDashboardHtml, _fichaBuildSpecPayload/_fichaBuildSpecFields. Adicionado ao pipeline de concatenação em build.cjs, posicionado depois de accessibility.js (consome A11Y_CATEGORIES/ switchA11yWorkspaceTab/a11yAreas/a11ySpecs/saveToStorage) e antes de onboarding.js. 8e. Reorganização estrutural (2026-09-08): artefatos soltos na Section de sessão, specs com réplica

Estrutura de canvas atual: uma Section de sessão por página (_getOrCreateA11ySessionSection, localizada só por pluginData hacSessionSection === 'true', nunca por nome — o nome carrega timestamp + designer e muda a cada sessão). Dentro dela, cada Área Marcada tem seu Grupo do selo/marcador (area.id = id desse Grupo, inalterado desde 2026-09-05), e cada tipo de artefato documentado nessa área — Ordem de Tabulação, Trilha de Swipe, Especificações (Leitor de Tela) — vive no seu PRÓPRIO grupo, solto irmão do Grupo do selo, nunca aninhado dentro dele. Uma reorganização anterior, na mesma sessão, tinha experimentado aninhar tudo dentro de 1 Grupo por Área; foi abandonada em favor deste modelo mais simples porque o destino final desses artefatos é a Ficha de Handoff (seção 8c), que os reorganiza de qualquer forma — o aninhamento por área não tinha propósito próprio.

Cada grupo de artefato = clone da área + grupo-overlay: o padrão, estabelecido primeiro por Tabulação e depois espelhado por Swipe e Especificações, é sempre o mesmo par:

  • Clone-réplica (root.clone()) do frame original da Área — nomeado [Ordem de Tabulação] .../ [Trilha de Swipe] .../[Leitor de Tela] .... Se a Área foi marcada sobre uma INSTANCE de tela publicada (padrão comum — arrastar a tela pronta da lib "DSC | Super App"), o clone também nasce INSTANCE; como a API do Figma proíbe appendChild nela, o clone passa por detachInstance() logo em seguida, virando FRAME — o frame ORIGINAL nunca é tocado, só esta cópia de trabalho perde o vínculo com o main component.
  • Grupo-overlay (_getOrCreateCloneOverlayGroup), IRMÃO do clone (nunca filho dele) — onde de fato vivem os selos de Tabulação, a linha de Swipe, ou os specGroups do Leitor de Tela. GROUP puro, nunca FRAME: nunca tem clipsContent nem Auto Layout, o que o torna estruturalmente imune ao bug descrito abaixo.

Por que não desenhar direto dentro do clone (histórico de causa raiz, relevante para não repetir o mesmo erro por um caminho diferente): a primeira versão desta arquitetura reparentava selos/linha DIRETO para dentro do clone. Cinco bugs reais apareceram em sequência, cada um só visível depois do anterior corrigido:

  1. Clone INSTANCE não aceita appendChild — resolvido com detachInstance() (acima).
  2. Selo nascia deslocado, nunca ao lado do elemento-alvo: escrever x/y antes de marcar layoutPositioning = 'ABSOLUTE' fazia o Auto Layout do clone (telas reais de produto podem ter) descartar a escrita e posicionar o selo em modo de fluxo.
  3. Selo nascia certo, mas atrás do elemento que deveria marcar: itemReverseZIndex = true (comum em frames com elementos sobrepostos de propósito — carrosséis, cards empilhados) inverte a pilha de z-order de um Auto Layout, colocando o PRIMEIRO filho no topo em vez do último; appendChild sozinho não bastava.
  4. Causa raiz definitiva: mesmo com as 3 correções acima, selos continuavam invisíveis — clipsContent em qualquer frame no caminho entre o clone-raiz e o selo recorta qualquer filho que "vaze" pra fora dos limites daquele frame, e um selo ao lado de um elemento pequeno vaza de propósito (mesmo problema afetaria uma linha de swipe cruzando a tela toda). Tirar o clipsContent do clone foi descartado — mudaria a aparência da própria réplica em telas com carrossel/scroll. A solução real foi arquitetural: nunca mais reparentar dentro do clone — sempre no grupo-overlay irmão dele (acima).
  5. Separado dos 4 anteriores, mas achado na mesma sessão: o cache de clone ativo em memória (_activeTabOrderCloneMap/ _activeSwipePathCloneMap, antes uma única variável global, não por área) fazia o backend "esquecer" o clone certo ao alternar entre Áreas na mesma sessão — voltar pra uma área e continuar a Tabulação recriava tudo do zero (apagando selos já feitos) e resolvia cliques contra o elemento ORIGINAL em vez do clone. Migrado para Map<areaId, nodeMap> (_activeTabOrderCloneMaps/_activeSwipePathCloneMaps/ _activeSpecCloneMaps) — cada área mantém seu próprio clone ativo, sem colisão entre áreas trabalhadas na mesma sessão.

Especificações (Leitor de Tela) ganham réplica: até esta mudança, create-unified-spec desenhava o marcador/ conector direto sobre o elemento original — única das 3 features de documentação que ainda tocava o design de verdade. Passou a seguir o mesmo padrão de Tabulação/Swipe: _resolveActiveSpecClone/_createSpecCloneForArea (mesma lógica de cache por área e detachInstance()) resolvem/ criam o clone da área, e o node resolvido a partir de opts.targetNodeId (id ORIGINAL, vindo do formulário/seleção) é traduzido pro node equivalente dentro do clone via nodeMap.get(...) antes de qualquer cálculo de posição. O spec.targetNodeId devolvido ao frontend continua sendo o id ORIGINAL (capturado ANTES da tradução) — outros fluxos (Detecção Automática marcando "já documentado", edição de spec, destaque no canvas) dependem desse id apontar pro elemento real, nunca pro clone. Specs sem Área Marcada associada (fluxo legado/manual sem área) continuam sem clone, apontando pro original, exatamente como sempre funcionou.

Lacuna fechada de propósito: specs nunca gravavam nenhum pluginData de área no próprio node — eram localizadas/apagadas só via array local (a11ySpecs, campo a11yAreaId), frágil se esse estado se perdesse. Specs novas gravam hacSpecForArea no specGroup; o handler delete-specs-for-area (espelhando delete-tab-order-copy-for-area/cleanup-swipe-path-for-area) localiza e remove clone + specs por esse pluginData, como rede de segurança independente do array local.

Varredura: as funções que localizam artefatos por pluginData (_forEachTabOrderCopyCandidate, _forEachSwipePathCopyCandidate, _forEachFichaFrameCandidate) ganharam uma 4ª fonte, _forEachA11ySessionDirectChild (filhos DIRETOS da Section de sessão, 1 nível) — somada às 3 já existentes (raiz da página, Sections antigas por prefixo de nome, e a varredura de 2 níveis _forEachA11ySessionAreaChild para áreas ainda na estrutura aninhada antiga). Nenhuma fonte antiga foi removida — mesmo princípio já usado em toda a base: nunca tirar uma fonte de varredura quando surge uma estrutura nova, para nunca deixar artefatos de qualquer geração órfãos/invisíveis. Sem migração retroativa: Áreas documentadas antes desta mudança continuam funcionando na estrutura aninhada, sem reprocessamento.

Outras correções da mesma sessão: o highlight temporário (retângulo [HighlightStroke], desenhado ao clicar em elementos durante a captura de Tabulação/Swipe, tanto no canvas quanto ao clicar num item da lista do modal de revisão) foi removido por completo — mesmo após duas rodadas de correção de condição de corrida em sessões anteriores, continuava deixando retângulos órfãos. O feedback visual passou a vir só da seleção nativa do Figma (figma.currentPage.selection), sem nenhum node extra criado. A posição da réplica clonada (_findFreeTabOrderCopyPosition) passou a nascer sempre ABAIXO do frame original, nunca mais tentando os 4 lados (direita/abaixo/esquerda/acima) em sequência. No fluxo de captura manual com seleção múltipla (shift+clique/marquise) de Tabulação/Swipe, _orderNodesInZigzagReadingOrder deixou de ser aplicado — esse algoritmo (inverte linhas alternadas, útil só para leitura de grade sem ordem de clique conhecida) estava descartando a ordem real de clique do designer, que o Figma já preserva em figma.currentPage.selection; a função continua em uso só por "Gerar Automaticamente" (que nunca tem ordem de clique real pra preservar).

Novo documento de processo: docs/funcionalidades-protegidas.md — lista de funcionalidades já testadas/aprovadas que exigem aprovação prévia explícita e explicação do impacto antes de qualquer mudança, criada depois de múltiplas regressões sucessivas na Ordem de Tabulação ao longo desta sessão.

8f. Ficha com 4 blocos horizontais (2026-09-08): ordem fixa, Swipe com réplica restaurada, Handoff Review

Layout final: a Ficha passa a ter 4 blocos em sequência horizontal única, na ordem fixa 1) Ordem de Tabulação, 2) Swipe, 3) Leitor de Tela, 4) Handoff Review — pedido explícito do usuário. O fichaFrame (_createOrGetFichaFrame) já era Auto Layout HORIZONTAL com primaryAxisSizingMode/counterAxisSizingMode = 'AUTO' nos dois eixos — isso já garantia mecanicamente "lado a lado, sem sobreposição, largura própria" para qualquer novo filho, sem precisar de nenhum ajuste de sizing. O que faltava era ordem determinística: antes, cada builder fazia fichaFrame.appendChild(section) direto — como appendChild sempre insere no último índice, a posição final de cada seção virava simplesmente "a ordem em que o designer clicou Inserir/Atualizar pela primeira vez em cada aba" (bug real: inserir Leitor de Tela antes de Tabulação colocava Leitor à ESQUERDA). Corrigido com FICHA_SECTION_ORDER (array fixo ['tabulacao', 'swipe', 'leitor', 'review']) e _insertFichaSectionInOrder, que calcula o índice correto contra essa ordem e usa insertChild antes do primeiro filho existente com ordem maior — a posição visual final sempre respeita 1-2-3-4, não importa a ordem de clique.

Bug real preexistente corrigido de passagem: _cloneAreaRootIntoFicha fazia root.clone() sem checar clone.type === 'INSTANCE' e sem detachInstance() — diferente de _createTabOrderCloneForArea/_createSpecCloneForArea, que já tinham essa correção desde a cadeia de 5 bugs resolvidos na seção 8e. Como o clone da Ficha entra direto no fluxo do Auto Layout, sem overlay group nem reparenting condicional, esse bug se manifestaria de imediato em qualquer área marcada sobre uma INSTANCE de tela publicada — corrigido aplicando o mesmo detachInstance() antes de _buildOriginalToCloneMap.

Swipe volta a ter réplica visual real (regressão de uma entrega anterior, identificada pelo próprio usuário: "definitivamente é pra se ter uma réplica"): _buildFichaSwipeSection deixou de desenhar só o texto "1. X → 2. Y..." e passou a clonar a área (_cloneAreaRootIntoFicha), traduzir cada ponto (id ORIGINAL, vindo de hacData.a11ySwipePaths) pro node equivalente dentro do clone via nodeMap, e desenhar a trilha real (linha + setas) com _buildSwipePathConnection — a mesma função já usada no canvas de trabalho, não duplicada. A trilha nasce dentro de um grupo-overlay IRMÃO do clone (_getOrCreateCloneOverlayGroup, mesma técnica da seção 8e) — nunca filha direta dele, pelo mesmo motivo de clipsContent já documentado: uma trilha cruzando a tela inteira tem ainda mais chance de "vazar" pra fora de um frame com clip no caminho do que um selo pontual. O texto simples vira fallback só quando há menos de 2 pontos resolvíveis no clone atual (elementos renomeados/removidos desde a última trilha).

  • Cards de status por seção já inserida (nome + contagem), a partir de payload.sectionsSummary.
  • Lista compacta de specs por categoria, a partir de payload.categoryBreakdown.

Handoff Review — mais 2 blocos (2026-09-09): hierarquia de títulos e itens decorativos

Expansão do 4º bloco com mais 2 listas, ambas montadas a partir de dado 100% real já rastreado em a11ySpecs — sem inventar checklist fixo de contraste/toque/valores (não existe como dado real no hac hoje):

8g. Simulação de leitura por voz da Ordem de Tabulação (2026-09-09)

Ferramenta interativa nova dentro da aba de Tabulação (fica só ali — não vira bloco na Ficha de Handoff): um botão "Simular leitura" narra em voz real, via Web Speech API nativa do navegador/Chromium do Figma Desktop (speechSynthesis — sem serviço externo, sem token novo, sem dependência nova), cada parada da Ordem de Tabulação já criada, com destaque sincronizado no canvas (highlight-node, mesmo mecanismo de focusNode) — como um leitor de tela faria de fato. Objetivo: dar ao designer um jeito rápido de "ouvir" a experiência que está documentando.

O tipo falado não é persistido: tabOrderItems (schema salvo) continua sem nenhuma coluna de tipo/role/categoria — só tem {id, number, label, conector, targetNodeId, targetNodeName, a11yAreaId}. O "tipo" de cada parada (ex. "Botão" antes do nome) é recalculado ao vivo a cada simulação, mesmo princípio de "nunca mentir dado antigo" já seguido no resto do hac: a spec pode ter sido criada há dias, e o node pode até ter trocado de componente desde então.

Arquitetura backend→frontend (Web Speech API só existe no iframe; o matching DSC→a11y só o backend resolve):

  1. Frontend (toggleTabOrderNarration, accessibility.js) manda resolve-tab-order-narration com areaId + a lista já ordenada ({targetNodeId, targetNodeName, number} de cada item, via _currentTabOrderItems).
  2. Backend (code.js), best-effort por item (try/catch nunca derruba o loop inteiro): resolve figma.getNodeByIdAsync → se INSTANCE/COMPONENT, extrai componentKey (mesmo padrão de generate-tab-order-from-layers) → _resolveDscComponentA11yMatch → usa match.a11yCategory (shortName) como tipo quando há match não-isUnmapped. Sem match DSC mas node ainda existe: fallback mínimo por node.type nativo (só TEXT → shortName sintético 'texto'; qualquer outro tipo nativo fica sem tipo falado, de propósito — um fallback amplo demais soaria impreciso vindo de um leitor de tela simulado). Node apagado/ movido: shortName: null, narra só o nome salvo.
  3. Backend responde tab-order-narration-resolved com {areaId, items: [{number, targetNodeId, targetNodeName, shortName}]}, na mesma ordem recebida (targetNodeName também é atualizado para o nome/label atual do node, via _findVisibleLabelText, caso tenha mudado desde a criação do item).
  4. Frontend traduz shortName → fala via o novo léxico A11Y_NARRATION_TYPE_LABELS (português) ou A11Y_NARRATION_TYPE_LABELS_EN (inglês), conforme o idioma escolhido no <select id="tab-order-narration-lang-{uid}"> ao lado do botão (accessibility.js) — deliberadamente SEPARADO de A11Y_COMPONENTE_LABELS, que tem nomes técnicos em inglês/misto (ex. "Radio Button") inadequados pra fala em português. Frase por parada: "{Tipo}, {Nome}" quando há tipo (ex. "Botão, Enviar" / "Button, Enviar"), só "{Nome}" quando shortName é null. Importante: só o TIPO e a pronúncia da síntese mudam de idioma — o NOME do elemento nunca é traduzido, vem sempre como está gravado no Figma (pedido explícito do usuário, 2026-09-09: "EN e PT só pela nomenclatura dos itens").

Percurso automático (_tabOrderNarrationAdvance): aperta uma vez, narra a fila inteira em sequência. Cada parada destaca o node ORIGINAL no canvas (focusNode — a Ordem de Tabulação opera sobre o canvas real, não a réplica da Ficha) e fala via SpeechSynthesisUtterance, com utterance.lang igual a 'pt-BR' ou 'en-US' conforme o idioma escolhido no seletor (lido uma única vez ao clicar em "Simular leitura", guardado em window._tabOrderNarration.lang — trocar o <select> no meio de uma simulação em curso não afeta a fila já em andamento). O avanço para a próxima parada usa o evento onend da utterance (nunca um setTimeout arbitrário estimando a duração da fala), com uma pausa fixa de 400ms depois, simulando o intervalo natural entre elementos de um leitor de tela real. onerror da utterance também avança (nunca trava a fila por uma voz indisponível/engine instável).

Botão com estado: enquanto ativo, "Simular leitura" (ícone play) vira "Parar simulação" (ícone square, _setTabOrderNarrationButtonState, troca ícone/cor por id="tab-order-narration-btn-{uid}") — clicar chama speechSynthesis.cancel() e interrompe o percurso imediatamente (_stopTabOrderNarration, único caminho de encerramento, também usado no fim natural do percurso — nunca deixa o botão preso nem o highlight aceso). Suporte a speechSynthesis é checado antes de iniciar; sem suporte, mostra toast explicando e não faz nada mais — nunca impeditivo pro resto da aba. 8h. Alerta de desatualizado + "Gerar handoff completo" (2026-09-09); renomeação "Ficha" → "Handoff Completo"

Problema real mapeado pelo usuário: os cards de status na aba Handoff (dashboard) só mostravam se uma seção já tinha sido inserida no canvas alguma vez (insertedAt) — nunca se ela ficou desatualizada depois disso. Cenário: o designer insere a Ordem de Tabulação, depois volta à aba de trabalho e edita/adiciona itens, mas esquece de clicar em "Atualizar" de novo — o canvas fica com dado velho, sem nenhum aviso visível.

Detecção por COMPARAÇÃO DE CONTAGEM, não por timestamp de edição (_fichaSectionIsStale, handoff-ficha.js): compara o itemCount/specCount gravado no momento da última inserção (area.handoffFicha.sections[key]) contra a contagem ATUAL, lida ao vivo das mesmas fontes já usadas por _fichaInsertSection (_currentTabOrderItems para Tabulação, hacData.a11ySwipePaths para Swipe, a11ySpecs filtrado por área para Leitor de Tela). Limitação aceita e intencional: editar o CONTEÚDO de um item já contado, sem mudar a quantidade, não dispara o alerta — mais simples, sem persistir nenhum campo novo. O card do Handoff Review herda o alerta por tabela (_fichaReviewIsStale): fica stale se qualquer seção-fonte (tabulacao/leitor, e swipe só quando a origem é mobile — mesmo filtro de sectionKeysForReview já usado em _fichaInsertSection) estiver stale, mesmo que o Review em si tenha sido inserido corretamente da última vez.

Visualmente, o alerta troca o ícone verde check-circle-2 por alert-circle em âmbar (#d97706, cor de ATENÇÃO — nunca vermelha, não é uma falha, é pendência de sincronização) e o texto passa a mostrar a contagem atual vs. a gravada (ex. "3 agora — handoff tem 2, clique Atualizar"). O botão "Editar" de cada card não muda — já leva pra aba certa, onde _fichaButtonLabel mostra "Atualizar Handoff Completo" (texto reconciliado em 8i) com base em insertedAt.

Botão "Gerar handoff completo" (_fichaGenerateCompleteHandoff(areaId), handoff-ficha.js; botão novo em _a11yWorkspaceTabHandoffDashboard, accessibility.js, ícone layers — escolhido pra não colidir visualmente com sparkles, já usado em "ou usar Mapeamento Automático" na mesma workspace): monta a lista de chaves candidatas (tabulacao/swipe/leitor/review, filtrando swipe fora quando a origem não é mobile) e filtra só as PENDENTES (sem insertedAt) ou STALE. Se qualquer uma de tabulacao/swipe/leitor entrar na lista, review é forçado a entrar também — o consolidado precisa refletir os dados que serão reinseridos nesta mesma rodada, mesmo que o Review isoladamente não estivesse stale. Nunca reprocessa as 4 incondicionalmente — só reinsere o que está pendente/desatualizado, mais rápido e sem retrabalho no canvas para seções já em dia. Lista vazia → showToast('O Handoff Completo já está atualizado.') e para.

Disparo SEQUENCIAL, não concorrente (uma seção por vez, aguardando a resposta do backend antes da próxima) — decisão deliberada depois de investigar _fichaHandleSectionInserted: (1) esse handler já faz saveToStorage() + _renderA11yWorkspaceTab() a cada resposta — disparar as 4 mensagens de uma vez faria o backend responder em ordem não garantida e essas reconstruções de DOM/storage se sobreporiam sem necessidade; (2) mais importante, review lê o estado já persistido das outras 3 seções (area.handoffFicha.sections, dentro de _fichaInsertSection) — se disparado em paralelo com tabulacao/leitor, corre risco real de montar o resumo ANTES da resposta delas ter sido persistida. Sequencial elimina esse risco por construção, já que review só dispara depois que as seções anteriores já resolveram. Implementado com uma fila de resolvers (_fichaPendingResolvers, mapa sectionKey → resolve) e uma versão "aguardável" de _fichaInsertSection (_fichaInsertSectionAwaitable) que registra o resolver antes de disparar a mensagem — _fichaHandleSectionInserted/ _fichaHandleSectionInsertFailed resolvem essa promise quando existir, sem alterar o comportamento do clique manual de "Inserir/Atualizar ficha" (que nunca registra resolver nenhum).

Renomeação "Ficha" → "Handoff Completo" (mesmo pedido, pura, sem mudança de arquitetura): continua sendo 1 artefato por ÁREA marcada (_createOrGetFichaFrame inalterado). Mudou todo TEXTO visível ao designer (botões, toasts, labels de card, guia "Entendendo as categorias") e o NOME dos frames/seções criados no canvas (fichaFrame.name → "[Handoff Completo] {label}"; as 4 seções internas → "Handoff Completo — Tabulação/Swipe/Leitor de Tela/Handoff Review"). Não mudou nenhum identificador interno de código (_ficha*, handoffFicha, hacFichaSection, hacFichaForArea como chaves de pluginData) — convenção de código, nunca visível, gerar diff sem benefício real. Caso especial resolvido com migração aditiva: a Section organizadora que agrupa os frames de todas as áreas era localizada por nome literal exato em _getOrCreateNamedSection (n.name === sectionName, sem pluginData — diferente de _findFichaFrameForArea/ _findFichaSectionInFrame, que já usam pluginData e por isso puderam ser renomeados livremente). Simplesmente trocar o literal de A11Y_FICHA_SECTION_NAME faria arquivos já existentes — com uma Section "hac — Ficha de Handoff" real no canvas — deixarem de ser encontrados, e a próxima inserção criaria uma Section NOVA duplicada, órfã da antiga. Migração puramente aditiva, decisão do usuário: A11Y_FICHA_SECTION_NAME agora vale 'hac — Handoff Completo' (usado em toda Section NOVA), A11Y_FICHA_SECTION_NAME_LEGACY guarda o nome antigo só para reconhecimento — nunca há rename in-place da Section existente no canvas, arquivos antigos continuam com o nome velho indefinidamente, apenas reconhecidos e reaproveitados sem duplicar.

Idempotente: se já existir uma imagem antiga deste clone dentro de targetSection, remove antes de criar a nova — cada "Atualizar" substitui a imagem, refletindo o estado atual da tela. Fallback se exportAsync falhar: cria um FRAME placeholder (mesmo tamanho, fundo cinza claro, Auto Layout centralizado) com o texto "Não foi possível gerar a prévia desta tela" — loga o erro via console.error, nunca lança a exceção adiante nem trava a montagem da Ficha.

_findCloneOverlaySibling deixou de buscar só por parentesco — mudança de maior risco desta entrega. Antes, o overlay era sempre encontrado como IRMÃO do clone (sibling.parent === clone.parent), premissa válida enquanto clone e overlay sempre se moviam juntos. Com o clone de trabalho NUNCA MAIS entrando na Ficha (permanece pra sempre na Section de sessão) enquanto o overlay CONTINUA sendo movido pra dentro da Ficha, a premissa "mesmo pai" quebra. Os 3 builders (_buildFichaTabulacaoSection/_buildFichaSwipeSection/ _buildFichaLeitorSection) trocaram a chamada única a _moveActiveCloneIntoFichaSection por duas etapas: (1) await _snapshotCloneIntoFichaSection(clone, section, pluginDataKey) e (2) _getOrCreateCloneOverlayGroup(clone, pluginDataKey, namePrefix) seguido de um appendChild manual do overlay pra dentro da seção quando ainda não estiver lá (overlayGroup.parent !== section). Toda a lógica defensiva existente (_rescueLegacyOverlayNestedInsideClone, seed permanente do GROUP) foi preservada — nada removido, só reorganizado entre a parte do CLONE (agora vira snapshot) e a parte do OVERLAY (continua grupo real movido/reaproveitado).

Por que os textos da Ficha não usam layoutSizingHorizontal='FILL': provado repetidamente que FILL empilhado sobre uma cadeia de pais Hug produz largura degenerada (~0) — o Figma não tem, nesse caso, nenhum ancestral FIXED real contra o qual esticar. Section de sessão sem auto-fit via API: SectionNode só recalcula tamanho/posição por interação manual do designer (duplo clique), nunca em resposta a chamadas da Plugin API. _fitSectionToChildren mede os filhos por absoluteTransform (posição real do node) + width/height declarados — não por absoluteBoundingBox, que em nodes com clipsContent=false inclui todo o transbordamento de selos/overlays. Chamada de novo sempre que algo SAI de ser filho direto da Section (ex.: o clone indo pro "[HAC] Handoff - {Func}"), não só quando entra — sem isso a Section ficava com o tamanho antigo, abraçando um espaço vazio. Migrar a Section pra FRAME com Auto Layout foi cogitado e descartado: o conteúdo é todo de posição livre, então o FRAME acabaria em layoutMode='NONE' de qualquer forma, sem ganho real, e a migração exigiria mover manualmente cada filho de Sections já existentes em arquivos de produção.

10. Escala da UI (--ui-scale) e position dos modais

body usa zoom (não transform) para os 3 níveis de escala do plugin ([1, 1.15, 1.3]) — mantido deliberadamente: zoom reflui o layout de verdade (afeta scroll, overflow, medidas reais), enquanto transform: scale() só afeta a pintura, exigindo compensação manual e frequentemente quebrando scroll do corpo.

Bug real corrigido: todo modal do hac usava fixed inset-0. position: fixed não cria novo containing block sob zoom — o containing block de um elemento fixed continua sendo o viewport real do documento, independente do zoom aplicado a um ancestral, mas o zoom do ancestral ainda é aplicado à pintura final. Resultado: o box do modal nascia do tamanho do viewport real e depois era escalado de novo, ficando maior que a área visível em qualquer escala > 100% (cortado, sem scroll).

Correção: todos os fixed inset-0 viraram absolute inset-0, e body ganhou position: relative — todo elemento que antes escapava do zoom via fixed agora resolve seu posicionamento contra o próprio body zoomado.

Bug real adicional: mesmo depois da correção acima, o card interno de 5 modais ainda limitava a própria altura com max-h-[85vh]/max-h-[92vh] — unidade de viewport, calculada contra a viewport real, não contra o body reescalado. Em qualquer escala diferente de 100%, o card podia nascer mais alto do que cabia, cortando o rodapé (botões de ação) para fora da área rolável interna. Corrigido trocando por max-h-full, que resolve contra o wrapper pai imediato.

10a. Onboarding — 1 jornada por origem (web/mobile)

Regra de produto (2026-09-09): existem exatamente 2 jornadas de onboarding — ONBOARDING_TOOLS.web e ONBOARDING_TOOLS.mobile (onboarding.js) — e os 3 pontos de entrada do produto SEMPRE convergem pra mesma fonte, resolvida pela origem atual do projeto (getA11yProjectOrigin()):

  • Banner "Primeira vez aqui?" (#onboarding-banner-web/ #onboarding-banner-mobile, specifications.html) — mostrado por maybeShowOnboardingBanner(), chamada dentro de navigate() (core.js) toda vez que a view alvo é view-specifications. Só o banner da origem atual fica visível — o outro é escondido explicitamente, mesmo que já tenha sido visto antes.
  • Ícone de chapéu ("Rever passo a passo", menu "Mais ações", specifications.html).
  • Escolha da lib na Home (chooseA11yHomeOrigin, accessibility.js) — só navega e deixa o banner acima decidir se aparece; não abre nenhum modal sozinha.

Os 3 chamam openOnboardingForCurrentOrigin(opts) (ou, no caso do banner/dismiss, as próprias maybeShowOnboardingBanner()/dismissOnboardingBanner(), também sem parâmetro) — nenhum ponto de entrada passa mais um toolKey fixo, todos resolvem via _onboardingKeyForCurrentOrigin().

Antes desta mudança existiam 4 entradas ('especificar', 7 passos genéricos, aberta pelo banner e pelo chapéu; 'lib-web-angular-react'/ 'lib-super-dsc-web'/'lib-super-app', 3 passos cada, disparadas automaticamente e sem ícone ao escolher a lib na Home) — o designer via um onboarding curto e específico da lib ao escolhê-la, e depois, se clicasse no chapéu, via um conteúdo diferente e mais longo. Fundido: cada jornada nova (web/ mobile) tem os 7 passos gerais + as particularidades que viviam nas entradas lib-* (categorias existentes na lib, hierarquia de Título, sub-variantes de Elementos e Imagens), numa sequência só. As 2 libs web (Web Angular&React/Super DSC Web) sempre tiveram texto quase idêntico e caem na mesma jornada web — o hac já reconhece as duas simultaneamente.

Estado "visto" sem migração retroativa: a chave de figma.clientStorage (hac-onboarding-seen) indexa por toolKey — como as chaves mudaram de especificar/lib-* pra web/ mobile, instalações que já tinham visto o onboarding antigo verão o banner aparecer mais uma vez (mesmo trade-off já aceito em outros campos aditivos do produto, sem migração).

11. Pendências conhecidas

Pendência de processo (não técnica): não existe mecanismo formal para a vertical de acessibilidade receber o sinal de componentes "Outro" (seção 6) — hoje é só um rótulo visível ao designer.

Versionamento maior (v1.x → v2.0) da Section de sessão (seção 8m): não implementado — não existe hoje, na UI real do hac, uma ação que corresponda de forma segura a "gerar um Handoff Completo do zero sobre uma área que já tinha documentação", distinta de "atualizar incrementalmente" (o único botão agregador existente, _fichaGenerateCompleteHandoff, é deliberadamente incremental por design). Requer, quando houver um gatilho de produto real e aprovado: (1) decidir a UI que dispara essa ação distinta da atualização normal, e (2) a lógica de replicar a Section inteira como nova versão major, preservando a anterior intacta (não só renomear/incrementar em cima da mesma Section, como o menor já faz).

Planejado — reidratação de hacData a partir do canvas (não implementado): o alerta de handoff próprio (seção 8p) hoje só INFORMA que já existe uma Section de sessão do designer atual — ele não repopula a11yAreas/a11ySpecs/ tabOrderItems/a11ySwipePaths a partir dela. Se o storage local (figma.clientStorage) também não tiver sobrevivido (troca de máquina, cache limpo, navegador diferente), o designer vê o alerta dizendo "você já documentou N telas aqui", mas a lista "Telas Documentadas" continua vazia até ele recriar tudo manualmente — contradição de UX que só não incomoda hoje porque o caso mais comum (reabrir o mesmo arquivo na mesma máquina) já é coberto pelo storage local de qualquer forma. Caso de uso real desta lacuna: retomar um handoff PRÓPRIO não finalizado no MESMO arquivo — não é migração de dados entre arquivos Figma diferentes, nem sincronização entre designers (isso é outro problema, fora de escopo aqui). Caminho recomendado para uma implementação futura: já que todo artefato de uma Área (selo, specs, clones de Tabulação/Swipe, Ficha) grava metadados suficientes via pluginData no próprio node do canvas (hacCategory, hacAreaTargetNodeId, e os pluginData específicos de cada tipo de spec/clone), o caminho é LER esses nodes já existentes dentro da Section de sessão encontrada e reconstruir os arrays de hacData em memória a partir deles — nunca recriar/desenhar nada novo no canvas, é puramente leitura de estado já persistido ali. Escopo dessa reidratação futura inclui decidir: (1) o gatilho de UI (automático ao detectar handoff próprio, ou uma ação explícita tipo "Recuperar documentação"), (2) o que fazer se hacData já tiver dados locais conflitantes nesse momento (mesclar, perguntar, ou só reidratar quando local estiver vazio), e (3) que pluginData de cada tipo de artefato hoje é suficiente para reconstruir o objeto completo (specs, por exemplo, guardam a maior parte do necessário nos nós de texto/spec já existentes, mas isso precisa de um levantamento próprio, não assumido aqui).

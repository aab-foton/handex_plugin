1. Por que este documento existe

O hac produz, no fim das contas, um artefato de handoff: um conjunto de decisões documentadas sobre como cada elemento de uma tela deve ser interpretado por tecnologia assistiva, prontas para o time de desenvolvimento implementar. O schema técnico (campos, tipos, validações) diz COMO esse artefato é representado em memória e em disco. Este documento diz O QUE cada peça do artefato SIGNIFICA — por que ela existe, o problema real que resolve, e de onde vem no fluxo de trabalho do designer dentro do Figma.

2. Áreas Marcadas (a11yAreas[])

O que representa: um agrupamento de contexto — geralmente uma tela, uma seção de tela, ou um fluxo específico dentro de um frame maior — que o designer decidiu tratar como unidade de trabalho para fins de handoff de acessibilidade. É o nível em que o hac organiza tudo o mais: toda spec de acessibilidade (seção 3) e toda revisão de Ordem de Tabulação (seção 4) pertence a exatamente uma Área Marcada.

De onde vem: criada manualmente pelo designer ("Marcar Área"), apontando para um nó real do canvas (targetNodeId) e recebendo um número sequencial (number) e um rótulo textual (label, até 80 caracteres — ver tecnico.html, seção 2). O número é o que aparece no selo visual desenhado sobre o frame no canvas (componente [a11y] Item Number/[a11y mob] Número da tela, ver tecnico.html, seção 8) — é a mesma numeração que o time de desenvolvimento usa para navegar entre a tela e sua documentação de acessibilidade.

Não representa nada sobre a tecnologia assistiva em si — é puramente estrutural/organizacional. A origem web/mobile do handoff não é mais um atributo por área (era, historicamente — ver tecnico.html, seção 3); hoje é uma característica do projeto inteiro (seção 5 abaixo).

3. Especificações de Acessibilidade (a11ySpecs[])

O que representa: este é o dado central do hac. Cada spec é uma decisão documentada sobre como um elemento específico da interface deve ser exposto para leitor de tela ou outra tecnologia assistiva — qual rótulo (accessibilityLabel) ele deve anunciar, se é decorativo e deve ser ignorado, que nível de título ocupa na hierarquia da página, que papel estrutural cumpre (landmark), ou que informação adicional (dica de uso, comportamento de foco) precisa ser comunicada ao desenvolvedor que vai implementar aquele componente. As 5 categorias (elemento, estrutura, titulo, decorativo, informacoes — detalhadas em tecnico.html, seção 2) são 5 tipos diferentes de decisão, não 5 níveis de importância.

Uma spec não é uma anotação livre: ela é estruturada porque precisa virar trabalho de implementação verificável — por isso tem campos obrigatórios por categoria/subtipo, limite de caracteres, e vínculo obrigatório a um componente real da lib DSC sempre que possível (princípio "componente real sempre, procedural só como último recurso", tecnico.html, seção 6). O campo properties[] ({key, label, value}) é o que carrega o conteúdo substantivo da decisão — por exemplo {key: 'label', value: '...'} é o texto que vai virar o accessibilityLabel real no código do app ou site (ver uso em src/plugin/modules/accessibility.js:1859).

De onde vem: duas origens possíveis no fluxo de trabalho (tecnico.html, seção 7):

  • Manual — o designer seleciona um elemento no canvas e preenche o formulário à mão, categoria por categoria.
  • Detecção Automática — o plugin varre um frame, reconhece instâncias de componentes DSC conhecidos e sugere uma categoria + preenchimento inicial (ex: nome do componente, quando resolvido). Mas nenhuma spec nasce da varredura sem revisão: todo item passa por confirmação individual no wizard antes de virar spec de fato — a varredura sugere, o designer decide.

Em ambos os casos, o dado final gravado em a11ySpecs[] representa a mesma coisa: uma decisão que o designer confirmou como correta para aquele elemento — seja porque ele mesmo a escreveu, seja porque aceitou (com ou sem edição) uma sugestão do plugin.

4. Ordem de Tabulação (tabOrderItems[])

O que representa: a sequência em que elementos interativos de uma tela devem receber foco de teclado/leitor de tela — uma dimensão de acessibilidade totalmente diferente das specs da seção 3 (que descrevem O QUE cada elemento é/anuncia; a ordem de tabulação descreve EM QUE SEQUÊNCIA o usuário navega entre eles). É a resposta documentada à pergunta "se eu navegar só de teclado/leitor de tela, essa é a ordem que faz sentido?".

De onde vem: nunca desenhada sobre o design original — sempre sobre uma cópia de frame clonada especificamente para esse fim, dentro de uma Section separada da Section de specs ("hac — Ordem de Tabulação", ver tecnico.html, seção 8). Populada por dois modos: clique manual sequencial do designer sobre os elementos da cópia, ou varredura automática que só sugere elementos reconhecidos como interativos (botões, campos, links, etc.) — em ambos os casos, o resultado é uma lista revisável (reordenável por arrastar, editável) antes de ser "Aplicada no Canvas" como selos numerados definitivos.

5. Origem do projeto (projectOrigin)

O que representa: não é uma decisão de acessibilidade em si — é uma configuração de contexto que determina COMO o restante dos dados deve ser interpretado e gerado. Um handoff web e um handoff mobile trabalham com catálogos de componentes DSC diferentes, campos diferentes (ex: React Native não tem hierarquia de heading H1-H6) e libs de matching diferentes — ver tecnico.html, seção 2 e seção 6. Por decisão de produto confirmada pelo usuário ("se é um projeto mobile, tudo referencia mobile"), essa configuração vale para o arquivo inteiro, nunca é mista dentro do mesmo projeto.

De onde vem: perguntada ao designer uma única vez por arquivo, na primeira ação que precisa saber a plataforma (Marcar Área com auto-detecção, Detecção Automática, ou Ordem de Tabulação) — nunca recalculada ou perguntada de novo depois disso, exceto na reabertura deliberada via modal "Sobre o hac" ou no "Reescanear" pontual dentro do resumo da Detecção Automática (exceção documentada em tecnico.html, seção 3).

6. Usuário identificado (currentUser)

O que representa: não é um dado de autoria/histórico de quem fez o quê dentro do handoff (o hac não versiona nem atribui specs a pessoas) — é só a identidade da sessão atual do Figma, capturada para fins de contexto de ambiente (ex: mensagens de boas-vindas, indicação de quem está usando o plugin naquele momento).

De onde vem: lida diretamente da API do Figma (figma.currentUser) no momento em que o plugin abre — { id, name, photoUrl }, sem processo de login próprio do hac (ver src/plugin/code.js:1743-1744). É por isso que clear-cache preserva currentUser ao zerar todo o resto: é identidade/configuração de ambiente, não conteúdo do projeto (ver tecnico.html, seção 1).

7. a11ySpecs[] como dado de treinamento — propostaProposta, não iniciada

Toda spec confirmada pelo designer — seja escrita manualmente, seja aceita a partir de uma sugestão automática — é, estruturalmente, um exemplo rotulado: "para este padrão de componente/contexto, esta foi a decisão de acessibilidade correta". É exatamente o tipo de dado que alimentaria um motor de aprendizado que aprimorasse as sugestões automáticas do próprio hac ao longo do tempo — ideia que já existe, embutida na filosofia de design do plugin, mas que hoje se resume a um único mecanismo determinístico real, não a aprendizado de fato:

O caso concreto já implementado é o pré-preenchimento do dropdown "Link do Componente", na variante mobile "Componente" de Elementos e Imagens: quando o nome do componente DSC resolvido pela varredura bate, por correspondência exata de nome, com um dos 46 nomes (de um catálogo de 64) que têm nodeId real conhecido, o <select> já nasce com essa opção selecionada — sem digitação manual do designer (ver tecnico.html, seção 5 e src/plugin/modules/accessibility.js, em torno da linha 1254). Isso é uma regra fixa de correspondência de nome, definida e mantida a mão pelo time — não aprende com o uso, não muda de comportamento com o tempo, e não usa nenhum histórico de confirmações passadas do designer.

A proposta discutida é diferente em natureza: um motor que observasse, ao longo do tempo, quais sugestões automáticas da Detecção Automática o designer confirma sem alterar (sinal forte de "a sugestão estava certa") versus quais ele edita ou descarta (sinal de "a sugestão estava errada ou incompleta"), e usasse esse histórico para melhorar a confiança e a precisão das sugestões futuras — por exemplo, priorizando qual categoria de acessibilidade sugerir primeiro para um componente DSC ambíguo, com base no que já foi confirmado antes para padrões parecidos.

Isto é uma proposta, não uma feature em desenvolvimento. Há considerações reais pendentes, sem resposta ainda:

  • Onde armazenar o histórico. O hac não tem backend próprio — roda inteiramente dentro do sandbox do plugin Figma, persistindo hoje só via figma.clientStorage, escopado por instalação do plugin e por arquivo (tecnico.html, seção 1). Um motor de aprendizado de verdade precisaria agregar sinal entre arquivos e, provavelmente, entre designers — o que clientStorage isolado por arquivo não permite hoje sem uma camada de infraestrutura nova.
  • LGPD/privacidade. Histórico de confirmações é, no fundo, dado sobre o comportamento do designer (o que ele aceita, edita ou descarta) — não é dado de saúde nem dado pessoal de usuário final, mas ainda é dado comportamental de uma pessoa identificável dentro da organização, e mereceria tratamento e transparência compatíveis antes de qualquer coleta.
  • Viabilidade no sandbox do Figma. Plugins Figma não têm acesso nativo a treinamento de modelo nem a um serviço externo próprio sem que o time monte e mantenha essa infraestrutura à parte — o que muda o escopo do projeto de "melhoria incremental do plugin" para "novo serviço com backend, armazenamento e ciclo de vida próprios".
  • ROI dado o volume de uso. Um motor de aprendizado só se justifica com volume suficiente de confirmações para gerar sinal estatístico confiável — vale checar se o volume real de uso do hac hoje chega perto disso antes de investir em construir a infraestrutura.

Em resumo: o dado já existe e já tem, em princípio, a forma certa para isso (spec confirmada = exemplo rotulado); o que não existe ainda é decisão, desenho de infraestrutura, nem validação de que vale a pena. Não iniciar esta frente sem pedido explícito e sem antes endereçar os pontos acima.

8. Sobre esta documentação

Este documento complementa a Documentação Técnica (schema, campos, contrato de mensagens) e não deve duplicá-la — mudanças de schema vão em tecnico.html; mudanças de significado/uso dos dados (novos tipos de dado, mudança do que uma categoria representa, evolução da proposta de aprendizado da seção 7) vão aqui. Ambos vivem como arquivos HTML estáticos dentro de docs/, no repositório privado — sem hospedagem pública.

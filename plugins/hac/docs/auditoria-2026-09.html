2. Arquitetura e dependências

Agente: architecture-guardian.

Schema hacData

  • _schemaVersion é decorativo — gravado como 1 desde a origem, nunca lido nem comparado em nenhum ponto do código. Toda evolução de schema foi tratada como aditiva (checagem de campo ausente + default), nunca por versão.
  • handoffFicha (por área) não está declarado no schema raiz de core.js — só existe descrito em handoff-ficha.js. O schema real do objeto a11yAreas[i] está fragmentado em pelo menos 2 arquivos.
  • a11ySwipePaths é a única estrutura sem variável de módulo espelhada (decisão documentada), criando uma assimetria de acesso em relação às outras 3 estruturas de topo.

Contrato de mensagens

  • 52 handlers no backend, ~44 tipos enviados pelo frontend, dispatcher único dos dois lados — estruturalmente saudável.
  • 4 handlers confirmados como código morto herdados do Handex, nunca removidos: edit-spec-connector, hide-spec-lines, lock-spec, get-node-main-text.
  • 3 padrões de tratamento de erro coexistindo sem convenção documentada de quando usar qual: figma.notify() silencioso, postMessage estruturado de falha, e try/catch totalmente silencioso (best-effort). 25 dos 52 handlers não têm try/catch próprio — a maioria são triviais, mas alguns manipulam árvore de nós com risco real de exceção não capturada (scan-frame, resolve-layer-order, start-tab-order-copy).

Divisão de módulos

accessibility.js concentra pelo menos 5 sub-domínios de tamanho médio-grande (300-850 linhas cada). Os 2 candidatos mais fortes e de menor risco para extração:

Sub-domínioLinhasPor que é candidato forte
Ordem de Tabulação727Fronteira de dados clara (tabOrderItems), 11 tipos de mensagem próprios, zero dependência de outros sub-domínios para funcionar.
Trilha de Swipe595Arquitetura espelhada da Tabulação por design, mesma independência.

Extrair as duas reduziria accessibility.js de 7.668 para ~5.750 linhas.

Diferenciação web/mobile — mecanismo

Bem aplicada nos fluxos auditados, mas implementada via checagem binária (=== 'mobile') espalhada em pelo menos 3 formas equivalentes de checagem, em vez de um enum/helper central único (ex. isA11yMobileProject()). Funciona hoje; seria ponto de dor real numa eventual 3ª origem de projeto.

Dívida técnica mais relevante

  • 36 comentários "bug real corrigido/confirmado" no total, concentrados em 3 polos: reparenting/clone/overlay, fluxo de lote de Detecção Automática, e Ordem de Tabulação/Swipe — sinal de que a arquitetura de clone-de-frame-para-anotação é o núcleo de risco estrutural recorrente do produto.
  • Lista de 16 categorias de a11y duplicada manualmente entre accessibility.js:129-134 (runtime) e build-dsc-a11y-mapping.cjs:92-96 (build script), com aviso em comentário para manter sincronizado à mão — sem checagem automática. Hoje idênticas (16/16), mas sem rede de segurança para a 17ª categoria.
  • docs/architecture-state.md está obsoleto e se autodeclara assim desde 2026-09-02, mas continua no repositório com aparência de documento vivo — docs/tecnico.html é a fonte real e atualizada.

3. Domínio de acessibilidade (specs, categorias, matching)

Agente: accessibility-specialist.

As 5 categorias — cobertura

Todos os textos didáticos são fiéis ao material extraído via REST API da lib "Design Acessível" — não há conteúdo inventado. Assimetria real notada: dentro de "Elementos e Imagens", alguns componentes têm Nota de Código técnica detalhada (Accordion, Checkbox, Dialog...) e outros só Descrição (Breadcrumb, Button, Inputs, Link) — vale confirmar com a vertical se é lacuna de conteúdo ou fidelidade real à lib.

Paridade entre os 3 fluxos + Handoff Completo

  • Tabulação é a mais completa (manual + automático + edição incremental + narração por voz).
  • Swipe alcançou boa paridade após a reformulação de 2026-09-09 (edição item-a-item, "+ Adicionar ponto", reordenar). Única lacuna: sem "Simular leitura" (razoável, já que é gesto, não narração sequencial — mas uma prévia textual da ordem dos pontos poderia ajudar a auditar sem reabrir "Editar pontos").
  • Leitor de Tela (aba de criação das 5 categorias) sem lacuna funcional identificada.
  • Handoff Review é 100% dado local já persistido — não envolve nenhuma chamada REST em runtime (a chamada REST do produto existe só no processo de curadoria offline via CI/Gemini).

Agente: data-design.

Estado do CI — refresh-dsc-refs.yml

Confirmado ao vivo via gh run list/gh api: as últimas 5 execuções falharam, todas com o mesmo erro (GitHub Actions is not permitted to create or approve pull requests). Mesmo corrigido o toggle, o workflow hoje só regenera o mapeamento DSC→a11y de web-angular-react e super-app — faltam as chamadas equivalentes para super-dsc-web e dsc-android, que só foram geradas manualmente/localmente. notify-hac-refs-update.yml tem a mesma lacuna (não reconhece dsc-android).

fetch-instruction-frames.cjs — inoperante desde a criação

Os nodeId dos frames de instrução estão fixos como null (TODO nunca preenchido) — o script roda toda semana no CI sem produzir nenhum artefato. Não quebra nada (tratamento gracioso), mas a feature de "coluna de instrução na Ficha/Handoff Completo" não tem nenhuma imagem disponível hoje, mesmo com o conteúdo textual já preenchido pelo Gemini.

Cobertura de scan raso vs. profundo

Confirmado: só a lib mobile de "Design Acessível" recebeu deep-scan até hoje (deepScan: true). As 4 libs de produção usadas pelo matching de a11y nunca tiveram deep-scan — fetch-design-refs.cjs usa exclusivamente o endpoint raso /v1/files/:key/components, nunca percorre a árvore completa via /v1/files/:key/nodes. Componentes DSC reais não publicados como "componente" formal do arquivo ficam invisíveis a todo o pipeline, incluindo o próprio inventário de cobertura.

dsc-structural-review.json — trabalho pronto sem consumidor

87 candidatos de baixa confiança já revisados estruturalmente (via REST API + curadoria), status: "preenchido". 80 confirmam o match atual; 7 trazem achados novos, incluindo 3 reais e concretos na lib mobile: [dsc-tc] Avatar Hero (deveria virar "imagem com cabeçalho", não como está hoje), [dsc-ts] Screen Input Money e [dsc-ts] Screen Item Select List (templates de tela inteiros que precisam ser decompostos em subcomponentes, não tratados como unidade única). Nenhum grep encontra referência a esse arquivo em build-dsc-a11y-mapping.cjs — o loop nunca fecha.

Consistência entre as 4 libs

  • Nomenclatura de arquivo de mapeamento não é 1:1 previsível a partir do slug da lib (sufixos históricos diferentes: sem sufixo, -mobile, -superdscweb, -android).
  • {slug}-properties.json está 8 dias mais antigo que {slug}.json em 3 das 4 libs — se algum component set foi renomeado nesse intervalo, o cruzamento por nome exato usado em build-a11y-constants.cjs falha silenciosamente (fail-open, sem aviso).
  • src/plugin/refs/README.md já se autodeclara desatualizado (nota de 2026-09-08) e não documenta boa parte dos scripts/arquivos reais do diretório.

5. UX e interface do plugin

Agente: design-ux.

Achado mais crítico desta frente

AltoToasts sem aria-live

#toast-container (build.cjs:242) e showToast (core.js:298-319) não têm role="status"/aria-live — nenhuma confirmação, erro ou mensagem informativa é anunciada a um usuário de leitor de tela navegando a interface do hac. Correção sugerida de esforço mínimo: aria-live="polite" no container resolve para todos os toasts de uma vez, sem tocar em cada chamada de showToast.

Consistência de nomenclatura "Handoff" vs. "Handoff Completo"

A renomeação da sessão não chegou a 2 lugares muito visíveis: a própria tab da workspace (specifications.html:231, ainda só "Handoff") e o botão de inserção individual dentro de cada aba de trabalho ("Inserir no handoff"/"Atualizar handoff", minúsculo, handoff-ficha.js:58). O card "Handoff Review" (handoff-ficha.js:434) também ficou em inglês/nome de variável, quebrando o padrão 100% PT-BR do resto do produto.

Fluxo de navegação

  • Ordem das tabs (Tabulação → Swipe → Leitor de Tela → Handoff) contraria a lógica operacional recomendada — o próprio onboarding instrui documentar specs (Leitor de Tela) antes de montar a Ordem de Tabulação, mas a tab correspondente vem em 3º lugar visualmente, sem nenhuma numeração ou indicação de "comece aqui".
  • 4 pontos de entrada diferentes para inserir a mesma seção no Handoff Completo (botão dedicado em cada aba de trabalho + botão individual no card do dashboard + botão consolidado "Gerar handoff completo") — funcionalmente correto, mas sem explicação de quando usar qual.
  • Tab Swipe continua clicável e visualmente igual às outras mesmo em projeto web (onde é sempre bloqueada) — só descobre-se a regra depois de clicar.

Onboarding

Estado geral bom — já consolidado em 2 jornadas (web/mobile) e sincronizado com a maior parte da estrutura atual. Duas lacunas pontuais: não menciona "Simular leitura" (com seletor de idioma) nem "Editar pontos" da Trilha de Swipe, ambas features do mesmo dia da última atualização do onboarding — e não menciona a existência do botão "Gerar handoff completo".

Tema claro/escuro em componentes recentes

Seletor de idioma da narração e botão "Editar pontos" do Swipe estão corretamente adaptados. Problema real e recorrente: os cards de status com alerta de desatualização (handoff-ficha.js:368-443) usam cor hex fixa via style="", sem variante dark — contraste calculado abaixo do mínimo WCAG AA no tema escuro para pelo menos 2 das 3 cores usadas (âmbar ~3,9:1, verde ~3,2:1, mínimo exigido 4,5:1). O mesmo padrão hardcoded se repete em pelo menos 2 outros pontos do dashboard.

Agente: design-system-specialist.

Já existe um documento de tokens formal e sério: docs/design-system.html (989 linhas, evidência por arquivo/linha). 2 bugs de token concretos encontrados

BaixoHover de cor incorreto em 4 botões

modals.html:544-546,610,698,901 — hover:text-blue-700/hover:bg-blue-700 resolve para #00335c na escala customizada do projeto, dois tons mais escuro que o padrão real usado em qualquer outro botão azul do produto (blue-600, #004782).

Duplicação de dado (não de padrão visual)

Solução de custo baixo: gerar esse bloco dinamicamente via JS a partir de A11Y_CATEGORIES no carregamento da view.

Recomendação explícita do agente

Não criar um arquivo de tokens JS/CSS centralizado agora — o projeto é enxuto por design, e o custo de uma camada de indireção nova supera o benefício de eliminar uma duplicação pequena (~30 linhas). Repropagar o documento já existente é a ação de maior retorno imediato.

Handex — Arquitetura de Dados

Este documento complementa o Modelo de Dados — lá está o schema (campos, tipos, convenção de nomenclatura no canvas); aqui está a semântica: o que cada tipo de dado que o Handex gera REPRESENTA no trabalho real de handoff entre design e desenvolvimento, de onde ele nasce no fluxo de uso do plugin, e — só onde fizer sentido real — uma reflexão honesta sobre potencial futuro de aprendizado automático. Não há schema técnico novo aqui; para campos/tipos, ver data-model.html.

1. Por que este documento existe

O Handex produz, no fim do processo, um artefato de handoff: um conjunto de decisões de design documentadas — o que cada elemento de tela deve fazer, como deve se comportar, que medidas e tokens do Design System CAIXA ele usa, como as telas se conectam entre si — prontas para o time de desenvolvimento implementar sem precisar perguntar ao designer no Slack ou adivinhar pelo protótipo. O Modelo de Dados descreve COMO esse artefato é representado (nomenclatura de nós no canvas, schema de handoffData no localStorage). Este documento descreve O QUE cada peça SIGNIFICA — por que ela existe, que tipo de conhecimento carrega, e de onde vem no fluxo real de trabalho do designer dentro do Figma.

Todos os tipos de dado abaixo foram confirmados lendo o código-fonte real em src/plugin/modules/*.js e src/plugin/code.js — não é uma lista aspiracional.

2. Especificações Anotadas (Spec) Confirmado no código

O que representa: uma decisão de comportamento ou aparência que o designer documentou sobre um elemento específico de uma tela — o que aquele botão faz ao ser clicado, que estado tem quando desabilitado, que regra de negócio governa aquele campo, que exceção pode ocorrer ali. Ao contrário do hac (plugin irmão, focado só em acessibilidade), o Handex usa categorias livres e customizáveis pelo próprio time (CATEGORY_COLORS, gerenciadas via "Gerenciar Categorias" — ver src/plugin/modules/specifications.js) — não há um conjunto fixo de 5 categorias como no hac. Isso reflete o escopo mais amplo do Handex: documentar qualquer aspecto de handoff, não só a11y.

Cada spec carrega um vínculo posicional (cardX/Y/W/H, guideSide) porque não é só texto solto — é uma anotação ancorada visualmente a um elemento real do design, com conector desenhado no canvas até o elemento anotado (ver seção 3.1 de data-model.html).

De onde vem: criada manualmente pelo designer ao selecionar um elemento no canvas ("Anotar Specs") e preencher categoria, nota e propriedades — não há hoje sugestão/preenchimento automático de specs no Handex (diferente do hac, que tem Detecção Automática por reconhecimento de componente DSC).

Potencial de aprendizado futuro: uma spec confirmada é, estruturalmente, um par (padrão de elemento → decisão documentada). Se o Handex algum dia ganhasse algum tipo de sugestão automática de categoria/conteúdo (o que não existe hoje), o histórico de specs já escritas seria o material bruto para isso — mas isso hoje é só uma leitura possível da estrutura do dado, não uma proposta em andamento.

3. Medidas (Measurement) Confirmado no código

O que representa: uma medida de espaçamento ou dimensão extraída de um elemento do design — padding, gap, largura, altura ou raio de borda, sempre com eixo (top/bottom/left/right/horizontal/vertical/all). É a resposta documentada à pergunta "quantos pixels tem esse espaçamento?", sem exigir que o dev abra o Figma e meça manualmente.

De onde vem: duas origens no fluxo de trabalho (src/plugin/modules/measurement.js): seleção manual de um elemento seguida de escolha do tipo/eixo a medir, ou escaneamento automático que lê as propriedades de auto-layout do próprio nó Figma (padding, gap já configurados no elemento) e sugere as medidas — sempre revisável antes de virar anotação definitiva no canvas.

Potencial de aprendizado futuro: pouco aplicável — é um dado quase inteiramente derivado de geometria/propriedades já existentes no arquivo Figma (o auto-layout já "sabe" o valor), não uma decisão de julgamento humano que um modelo precisaria aprender a replicar.

4. Fluxos de Tela (Flow) Confirmado no código

O que representa: uma conexão de navegação entre duas telas do projeto — "da tela de Login, ao clicar em Entrar, vai para a Home" — incluindo pontos de decisão (gateways condicionais) quando o fluxo se ramifica. Reunidos, os fluxos formam jornadas (agrupamento calculado por computeFlowJourneys, reaproveitado tanto pela tela de Fluxos quanto pela Ficha de Handoff — nunca duplicado) — o mapa de navegação completo de um caso de uso, do início ao fim.

De onde vem: desenhado manualmente pelo designer clicando em sequência nos frames do canvas, na ordem real de clique do usuário (não a ordem de criação dos frames) — ver decisão de produto registrada no histórico de mudanças de Fluxos de Tela (reforma de 2026-08). Tipos de conexão incluem line_solid, line_dashed, diamond (decisão) e diamond_dashed; existe ainda um tipo gateway_parallel no código (specifications.js, em torno da linha 3654) que hoje não é oferecido na criação normal nem no reaproveitamento entre tipos ao editar uma conexão — o comentário no código não explica o motivo, então fica em aberto se é uma variante BPMN reservada para uso futuro ou resíduo de uma iteração anterior do editor de fluxos.

Potencial de aprendizado futuro: jornadas completas são o tipo de dado mais próximo de "conhecimento de produto" que o Handex acumula — se um mesmo padrão de fluxo (ex: gate de autenticação antes de uma ação sensível) se repete entre projetos, isso poderia em tese informar sugestões de fluxo padrão no futuro. Puramente especulativo hoje: não há mecanismo nenhum, nem proposta formal, que leia fluxos de um projeto para sugerir algo em outro.

5. Conformidade DSC / Tokens Escaneados Confirmado no código

O que representa: o resultado de um batimento automático entre os elementos de um frame e o catálogo de componentes/tokens do Design System CAIXA (DSC) — para cada item, se ele usa um token reconhecido, se diverge do padrão, ou se está totalmente fora do DSC. É um dado de auditoria de conformidade, não de decisão de design: o Handex não decide se o desenho está certo, só relata o que encontrou comparado ao catálogo oficial.

De onde vem: gerado por scanFrame() (src/plugin/modules/specifications.js), que roda automaticamente e complementa (nunca substitui) a declaração humana de conformidade feita pelo designer por frame (campo audit: semDesvios, observacoes, ressalvas) — ver src/plugin/modules/specifications.js:20-21. O escopo do scan (quais libs DSC considerar) é escolhido pelo designer via selectedLibSlugs.

Potencial de aprendizado futuro: este é o tipo de dado mais estruturalmente próximo de treinar algo — cada item escaneado já vem rotulado (conforme / com desvio / fora do DSC) por comparação automática contra um catálogo, mais a confirmação humana por cima. Ainda assim, hoje o batimento já é 100% determinístico (regra de correspondência, não aprendizado), e não existe proposta formal de ir além disso no Handex.

6. Ficha de Handoff (canvas + exportação) Confirmado no código — feature ativa, não oculta

O que representa: o documento consolidado final que reúne tudo o que foi documentado num projeto — dados do projeto, briefing, especificações, medidas, fluxos e conformidade DSC — num único artefato pronto para entrega ao time de desenvolvimento. É literalmente o produto final do Handex: tudo o mais no plugin existe para alimentar este documento.

A Ficha existe em duas formas, geradas pelo mesmo botão "Gerar Ficha de Handoff":

  • Ficha Técnica no canvas — um frame Figma real, composto de cards (Ficha de Projeto, Briefing, Interface), nomeado Handex | Ficha de Projeto | {título} | {timestamp}, que atualiza em vez de duplicar quando já existe uma versão anterior (src/plugin/code.js, função _hdFindExistingFicha). Nasce destravada, ao contrário de Specs/Medidas/Fluxos individuais, que nascem bloqueados.
  • Ficha Técnica HTML interativa — um arquivo .html autocontido (Tailwind + Lucide embutidos), gerado por getInteractiveHTMLContent() (src/plugin/modules/handoff.js:676), com abas, acordeões por categoria, lightbox de imagens e chips de Code Connect. Este arquivo é empacotado junto com Markdown e PDF dentro de um único ZIP pelo botão "Exportar Handoff (ZIP)" (exportHandoff(), handoff.js:485).

Sobre a hipótese de uma "Ficha em HTML oculta": a investigação de código não encontrou nenhuma feature flag, condição sempre-falsa, comentário de "desligado" ou UI ausente relacionada à Ficha em HTML — ela é gerada pelo mesmo botão visível na tela de Resumo do Handoff, documentada passo a passo em guide.html, e aparece em dezenas de commits de correção de bug ao longo do histórico do plugin (não uma feature esquecida). O DATA_MODEL.md tem uma seção chamada "Roadmap HTML/SharePoint" (seção 7) que soa como algo futuro/pendente, mas descreve exatamente esta exportação já implementada — é a documentação técnica que está desatualizada nesse ponto, não a feature que está oculta.

De onde vem: consolidação de todo handoffData no momento em que o designer clica em "Gerar Ficha" — nunca gerada automaticamente ou em segundo plano.

Potencial de aprendizado futuro: a Ficha em si é um dado de saída (agregação do que já existe), não uma nova fonte de sinal — o aprendizado, se algum dia existir, aconteceria sobre os dados de origem (specs, conformidade DSC), não sobre o documento consolidado.

7. Contexto de Negócio e Briefing Estratégico Confirmado no código

O que representa: o "porquê" por trás da entrega — problema que está sendo resolvido, decisões estratégicas, regras de negócio e histórias de usuário associadas, cenários de exceção previstos. Existe para que o dev entenda a motivação da tela antes de mergulhar na implementação, sem precisar perguntar de novo algo que já foi decidido em outra reunião.

O Briefing Estratégico é organizado por eixos temáticos (BRIEFING_AXES, ex: Contexto do Projeto) com perguntas sugeridas por eixo mais espaço para perguntas customizadas — módulo extraído para src/plugin/modules/briefing.js em 2026-08 por ter crescido a ponto de justificar arquivo próprio.

De onde vem: preenchido manualmente pelo designer, com opção de importar de um framework de briefing externo em Markdown (importBriefingMD) ou puxar diretamente de um frame já existente no canvas (pullBriefingFromCanvas).

Potencial de aprendizado futuro: não se aplica no mesmo sentido dos dados de specs/DSC — briefing é texto estratégico livre e específico de cada projeto (às vezes sensível: escopo, riscos, contexto pré-lançamento), não um padrão repetitivo com "resposta certa" que um modelo aprenderia a prever. Tratamento equivalente a este já foi avaliado no hac (ver Modelo de Dados) e descartado como direção de aprendizado de máquina justamente por essa natureza sensível do conteúdo — a mesma ressalva se aplica aqui.

8. Dados de Projeto (step1) Confirmado no código

O que representa: a identidade e metadados administrativos da entrega — título, versão, objetivo, status do handoff (rascunho / em revisão / pronto para dev / finalizado), jornada, feature e equipe responsável. Não é conhecimento de design nem de negócio propriamente dito — é o cabeçalho que situa tudo o mais: aparece no topo da Ficha final para orientar o dev antes de entrar nos detalhes.

De onde vem: preenchido pelo designer na tela "Dados do Projeto" — Título, Versão e Objetivo são obrigatórios para liberar o botão "Gerar Ficha"; ao menos um membro de equipe com nome preenchido também é exigido (ver guide.html, passo a passo de Dados do Projeto).

Potencial de aprendizado futuro: não se aplica — é metadado administrativo, não uma decisão de padrão replicável.

9. Usuário identificado (currentUser) Confirmado no código

O que representa: não é um dado de autoria/histórico de quem editou o quê (o Handex não versiona nem atribui specs a pessoas) — é só a identidade da sessão atual do Figma, capturada para contexto de ambiente (mensagens de boas-vindas, saudação, indicação de quem está com o plugin aberto naquele momento).

De onde vem: lida diretamente da API do Figma (figma.currentUser) no momento em que o plugin abre, sem processo de login próprio do Handex.

10. _aiContext — contexto oculto para geração externa Confirmado no código — feature genuinamente oculta

Esta é a única feature encontrada na investigação de código que corresponde, de fato, à descrição de "oculta/desligada" — mas não é uma Ficha em HTML. É um campo JSON, não um documento visual.

O que representa: um agregador compacto de tudo o que já foi documentado num projeto — briefing respondido, telas documentadas (com contagem de specs/medidas e status de conformidade DSC), tokens DSC usados (ordenados por frequência), cenários de exceção, medidas e jornadas de fluxo — formatado para servir como material de apoio a colar em ferramentas externas de geração de design por IA (ex: Figma Make) ao propor uma tela nova dentro do mesmo projeto. Não é geração feita pelo Handex, nem integração automática — é um "prompt pronto" que o designer copia manualmente.

Onde fica o código: src/plugin/modules/design-data.js:14-93, função _buildAiContext(). O próprio comentário no topo do arquivo (linha 14) descreve a feature nestes termos exatos: "FEATURE OCULTA (2026-08), sem UI/botão visível ainda".

Como é exposta hoje: nunca por um botão próprio — o campo _aiContext é calculado sob demanda e inserido silenciosamente dentro do JSON gerado por "Exportar Handoff" (exportHandoffData(), design-data.js:95-107). É dado derivado, nunca persistido dentro do próprio handoffData — ao reimportar um JSON, o campo é deliberadamente removido antes de aplicar o estado (design-data.js:132: "nunca deve entrar em handoffData como estado persistido, senão reexporta/salva um snapshot congelado em vez de recalcular a partir do estado atual").

Por que está oculta — não é dedução, está documentado: docs/figma-api-roadmap-2026.md, item 4b, registra a decisão de produto por trás disso. Resumo fiel ao documento: não existe hoje nenhuma API que permita um plugin do Figma Design empurrar contexto para dentro do Figma Make — são superfícies de produto separadas, sem canal programático entre elas; o único caminho real é o designer copiar/colar manualmente. A versão mais ambiciosa (agregar briefings de VÁRIOS projetos numa base de conhecimento institucional buscável) foi avaliada e descartada por dois motivos: exigiria uma categoria de infraestrutura diferente (busca semântica/RAG, vector store, pipeline de ingestão), e briefings estratégicos são o conteúdo mais sensível que o Handex coleta (decisões de escopo, riscos de LGPD/compliance ainda não revisados, contexto pré-lançamento) — elevar isso a "fato institucional buscável" sem dono de curadoria é risco de governança que o Handex não deveria decidir sozinho.

Em resumo: a feature existe, funciona, e está no JSON exportado hoje — só não tem botão nem menção na UI porque foi implementada de forma deliberadamente contida, como material de apoio para copiar/colar, não como integração.

11. Dados que ficam de fora de propósito

Nem todo dado salvo pelo Handex é sobre o projeto. A ordem dos 6 cards da home (HOME_CARD_ORDER_KEY, src/plugin/modules/home-cards.js) e a preferência de tema claro/escuro são persistidas em localStorage, mas nunca em handoffData nem em nenhuma exportação — são preferências pessoais de uso do plugin, não conhecimento sobre a entrega. A distinção importa para esta página: um dado só entra na discussão de "potencial de aprendizado futuro" quando representa uma decisão sobre o produto sendo documentado, não uma preferência de interface.

12. Sobre esta documentação

Este documento complementa o Modelo de Dados (schema, campos, convenção de nomenclatura) e não deve duplicá-lo — mudanças de schema vão em data-model.html/DATA_MODEL.md; mudanças de significado/uso dos dados (novos tipos de dado, mudança do que uma categoria representa, evolução de qualquer proposta de aprendizado futuro) vão aqui. Ambos vivem como arquivos HTML estáticos dentro de docs/site/, no repositório privado — sem hospedagem pública.
